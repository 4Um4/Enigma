# ENIGMA — Полный обзор проекта

---

## 🎯 Что такое Enigma

Enigma — это локальная компьютерная RPG в жанре D&D 5e, где роль Мастера Подземелий, всех NPC и самого живого мира выполняют языковые модели (LLM), запущенные **полностью на вашем компьютере**, без облака и интернета. Игрок пишет действие в чат — мир отвечает. Никаких скриптов, никаких заготовленных диалогов. Каждая сессия уникальна.

Ключевая философия проекта, которую вы сформулировали сами:

> *"Цифры в коде → LLM интерпретирует → Игрок видит текст. NPC умный не потому что думает 24/7, а потому что помнит свою жизнь и реагирует через систему драйвов."*

## 🖥️ Характеристики компьютера

| Компонент | Значение | Следствие |
|---|---|---|
| GPU | RTX 3070 Ti | **8 GB VRAM** — жёсткий потолок |
| CPU | Intel i7-9700F | 6 физических ядер (8 логических) |
| RAM | 16 GB | Достаточно для одной сессии |
| ОС | Windows 11 Россия | Кириллица в путях, BAT-скрипты |
| Python | 3.11.9 в .venv | Фиксированная версия |

**Главное ограничение всей архитектуры:** 8 GB VRAM не позволяют держать больше одной модели одновременно. Это не баг — это аксиома, вокруг которой выстроена вся система lazy loading.

**Реальный VRAM-бюджет:**
```
ОС + CUDA runtime:     ~500 MB
Qwen3.5-9B Q4_K_M:   ~5300 MB  ← текущая основная модель
KV-cache (ctx=2048):   ~260 MB
Буфер безопасности:    ~700 MB
─────────────────────────────
Итого:                ~6760 MB  (82% VRAM)
```

Из логов видно что сейчас грузится именно **Qwen3.5-9B** (5.28 GiB), не Qwen2.5-7B как планировалось. Это важно — 9B тяжелее и медленнее, но умнее.

## ⚙️ Как работает система (технически)

### Цепочка одного хода игрока

```
Игрок: "осмотреться"
         ↓
[index.html] POST /api/game/action
         ↓
[routes.py] game_action()
  → проверка сессии игрока
  → формирование ChatTurnRequest
         ↓
[orchestrator.py] run_turn()
  ↓
  [1] rules_agent.run()          ← ModelPool.switch("saiga")
        llama-server POST /completion
        ← rules_result: {}
  ↓
  [2] npc_agent.run()            ← ModelPool.switch("npc_major")  
        llama-server POST /completion
        ← npc_result: {реакции NPC}
  ↓
  [3] dm_agent.run()             ← ModelPool.switch("qwen_7b")
        llama-server POST /completion
        ← dm_result: {dm_response, npc_reactions, world_changes}
  ↓
  запись в LayeredMemory (JSONL)
         ↓
[routes.py] → {response: "..."}
         ↓
[index.html] → отображение ответа
```

### ModelPool — сердце VRAM-оптимизации

```
Запрос агента "dm":
  1. Текущая активная модель != "qwen_7b"?
  2. → _unload_active_model()   ← Python GC освобождает память
  3. → _load_model("qwen_7b")   ← llama-server перезагружает модель
  4. → agent.run() → HTTP POST /completion
  5. → ответ возвращается в orchestrator
```

Переключение занимает 3–15 секунд. Это неизбежная цена 8 GB VRAM.

### Слоистая память (LayeredMemory)

```
world_canon_{world_id}.jsonl        ← факты мира (постоянные)
campaign_memory_{campaign_id}.jsonl ← история кампании (растёт)
session_memory_{campaign_id}.jsonl  ← события текущей сессии
npc_memory_{campaign_id}.jsonl      ← память NPC
```

Всё хранится в JSONL-файлах. При каждом ходе агенты читают последние N записей как контекст.

## 🔍 Важные наблюдения из логов

**1. Модель не та.** В `start_llm.bat` прописан путь к `qwen2.5-7b`, но llama-server реально грузит `model.gguf` который оказался **Qwen3.5-9B**. Это объясняет хорошее качество ответов, но 9B медленнее 7B примерно на 30–40%.

**2. Скорость генерации отличная.** Из логов llama-server:
```
prompt eval:  2.9 ms/token  (344 tok/sec)  ← префилл быстрый
eval time:   15.3 ms/token  ( 65 tok/sec)  ← генерация нормальная
total:       8.24 сек для 512 токенов
```
65 токенов/сек для 9B модели на RTX 3070 Ti — хороший результат.

**3. Ответ обрезается.** `stop_type: "limit"` — модель упёрлась в 512 токенов. Ответ не завершён. Нужно увеличить `max_tokens` для DM агента.

**4. Локация "unknown".** World agent получает пустой контекст. Нужно добавить начальную локацию в `campaign_state.json`.

**5. NPC и Rules агенты — заглушки.** Файлы `npc_major.gguf` и `npc_mass.gguf` в `data/` — нулевые (placeholder). `saiga.gguf` тоже. Фактически все три агента сейчас либо падают тихо (возвращают `{}`), либо используют fallback на основную модель.


**0.2.** В `start_llm.bat` увеличить `max_tokens`:
```bat
set "MAX_TOKENS=800"
```
Или добавить параметр `-np 800` в запуск llama-server. Иначе DM всегда обрывается на полуслове.

**0.3.** В `start_llm.bat` явно указать путь к нужной модели и добавить `-ngl 33` (все слои в GPU) поскольку сейчас часть идёт на CPU.

### Этап 1 — Стабильный игровой цикл (1–2 недели)

Цель: игрок может провести полноценную сессию без технических сбоев.

**1.1. Streaming токенов (SSE)**
Самое важное для UX. Сейчас 8–30 секунд тишины — это неприемлемо. С streaming первый токен появляется через ~500ms, и текст печатается по мере генерации как в ChatGPT.

Нужно создать:
- `backend/app/api/routes_stream.py` — SSE эндпоинт
- В `index.html` — обработчик `EventSource`
- В `llama_cpp_provider.py` — режим `stream: true`

**1.2. Одна реальная модель для всех агентов**
Поскольку NPC и Rules модели — заглушки, нужно временно переключить всех агентов на одну рабочую модель (Qwen3.5-9B) через `agent_model_map`. Качество сразу вырастет — один умный DM лучше трёх сломанных.

**1.3. Контекст в промпте**
Сейчас промпт DM агента получает `location: unknown` и пустую историю. Нужно подключить реальные данные из памяти.

**1.4. Отображение HP и статуса**
В `index.html` уже есть панель персонажа. Нужно связать её с реальным `/api/characters/demo-campaign` и обновлять после каждого хода.

---

### Этап 2 — Живые NPC (2–4 недели)

Цель: NPC перестают быть эхом DM и становятся самостоятельными персонажами.

**2.1. Система психологии NPC (из вашего Plan.md)**

Это ваша главная идея и она блестящая:
```
Python вычисляет (мгновенно, без LLM):
  stress=65, drive="fear", trust=-20, threat_level=HIGH
  → NPC готов к предательству

LLM получает короткий промпт с готовыми числами:
  "Карвен: страх=65, доверие=-20, угроза=HIGH. Реплика:"
  
Игрок видит:
  "— Как хотите, господин... — тихо, опуская глаза"
```

Файлы для создания: `npc_cognition.py`, `psyche_engine.py`, `threat_assessor.py`

**2.2. Система репутации**
Глобальная репутация (-100..+100) + индивидуальное доверие NPC. Чистый Python, без LLM, <50ms. Влияет на то что NPC скажут и сделают.

**2.3. Память NPC**
Каждый важный NPC помнит взаимодействия с игроком. Реализуется через `npc_memory_{campaign}.jsonl` + краткое резюме в промпте.

### Этап 3 — Богатый мир (4–6 недель)

**3.1. RAG по PDF книгам D&D**
У вас уже есть 6+ книг на русском в `pdf_drop/`. Нужно:
- Проиндексировать PDF → чанки текста
- Создать векторную базу (ChromaDB или FAISS — работают локально)
- При каждом ходе искать релевантные правила и лор

После этого модель будет знать конкретные правила, NPC, локации из ваших книг. Гандрен будет Гандреном, а не выдуманным персонажем.

**3.2. Мировой симулятор в фоне**
Каждые 15 минут реального времени World Agent делает тик: торговцы переезжают, слухи распространяются, злодеи двигаются к цели. Игрок возвращается в мир который жил без него.

**3.3. Полные правила боя**
Инициатива, сохранения, заклинания, условия (отравлен, оглушён). Сейчас есть только базовый скелет.

## 💡 Предложения

### Немедленно стоит сделать

**Один промпт вместо трёх агентов.** Сейчас pipeline: rules → npc → dm означает три переключения модели по 3–15 сек каждое. Итого 9–45 секунд накладных расходов на каждый ход *до* генерации. Для первого рабочего прототипа разумно временно объединить всё в один DM промпт который включает в себя роли rules и npc. Это снизит время хода с 40–90 сек до 10–20 сек.

**Добавить `<think>` блоки Qwen3.** Ваша модель Qwen3.5-9B поддерживает режим размышления (`thinking=1`). Если включить его, модель сначала думает (невидимо для игрока), потом отвечает. Качество нарратива заметно вырастет — особенно в сложных социальных ситуациях с NPC.

**Сохранить первую успешную сессию.** Сейчас при перезапуске сервера сессия теряется. Файл `data/sessions/demo-campaign.json` существует, но память сессии хранится в JSONL. Нужно убедиться что история не обрезается.

### Архитектурно важно

**Не добавлять новые модели NPC пока не заработает один DM.** Соблазн велик — купить специализированные NPC модели. Но пока нет streaming, нет стабильного контекста и нет RAG — качество определяется не моделью, а промптом и данными. Один умный Qwen с хорошим промптом переиграет трёх специализированных моделей с плохим контекстом.

**Зафиксировать текущий рабочий коммит в git.** Это первая точка где всё запускается. Она бесценна как baseline.
