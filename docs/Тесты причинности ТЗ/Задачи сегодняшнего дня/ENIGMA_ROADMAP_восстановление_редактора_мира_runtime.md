### A.1. Правила работы архитектора (обязательные)

1. Порядок фаз — раздел F. Не начинать фазу N+1 до закрытия всех пунктов фазы N, кроме явно помеченных «независимый».
2. Каждый пункт закрывается по контракту раздела I: реализация + проверки + подтверждение критериев + запись в MD. Пункт без записи считается открытым.
3. Координатный контракт (раздел D.1) — блокирующий. Любое изменение координатных полей до принятия контракта запрещено.
4. Запрещено: менять географию мира (ID узлов/локаций, двери/переходы, топологию), удалять/переносить пользовательские данные и сейвы, убивать чужие процессы и принудительно освобождать порты, добавлять двери/узлы/переходы «ради тестов».
5. Запрещено создавать второй источник истины. Все производные данные (compiled-реестр, staging-копии, runtime-состояние) должны иметь одного владельца и задокументированную инвалидацию.
6. При обнаружении неверного решения плана — статус `[!] REJECTED / REDESIGN`, причина и корректировка плана записываются в MD. Молча менять требования запрещено.
7. Ограничение по NPC: полноценную систему управления произвольным NPC игроком в текущий план НЕ включать. Восстанавливается только существующая самостоятельность NPC (координаты, движение, отображение, действия).
8. Расширения функциональности (World Editor, Asset Library) включаются только при явной привязке к устранению P1–P4 или к проверяемой игровой/редакторной возможности.

### C-P1. Стартовая сцена: игрок «у городских ворот» вместо интерьера таверны

1. **Симптом.** Новая игра логически стартует в `tavern` (метаданные, оракул, спавн-узел корректны), но первый кадр окружён геометрией `city_gate`; NPC таверны вне экрана.

**Отвергнутая альтернатива — «гибридный фрейм» (вариант H: геометрия мировая, сущности локальные в одном файле):** точно соответствует сегодняшнему поведению кода, но (1) противоречит миграции/валидатору/`create_location` редактора и «единой системе мировых координат» ТЗ; (2) делает холст редактора расщеплённым (стены и NPC на одной канве в разных фреймах); (3) требует вечной пары правил «какое поле в каком фрейме» в каждом новом потребителе. REJECTED по совокупности.

**Отвергнутая альтернатива — «учить `build_geometry` читать фактический фрейм» (RCA-1 F1-альтернатива):** второй источник истины фрейма в рендере; REJECTED (согласуется с RCA-1).

### D.3. Контракт синхронизации данных (безопасность зеркала)

Обязательные условия до реализации mirror-delete (запрет ТЗ на «очистку без доказательства владения» соблюдён):

1. **Абсолютный корень sync** — вычисляется от `__file__` `campaign_manager.py` (не от CWD): `parents[2]` от `frontend/map_editor/campaign_manager.py` = корень репо.
2. **Допустимые цели (белый список, константа кода):** `<root>/saves/{campaign_id}/locations/`, `<root>/build/staging/saves/{campaign_id}/locations/`, `<root>/build/staging/frontend/map_editor/campaigns/{campaign_id}/locations/`. Иных целей нет и не добавляется.
3. **Принадлежность кампании:** цель оперируется только если её путь после нормализации (`resolve()` + проверка `is_relative_to(root)`) совпадает с шаблоном белого списка И содержит текущий `campaign_id` из `cm.campaign_path.name`.
4. **Владение файлами:** mirror-delete применяется ТОЛЬКО к `*.json` внутри `locations/` цели, имя которых отсутствует в source-каталоге. Вложенные/посторонние файлы (не `*.json`, другие каталоги) — не трогаются, пишется warning.
5. **Неизвестные файлы:** файл в цели, которого нет в source — удаление (это и есть устаревшая копия); файл в source, которого нет в цели — копирование; ошибка чтения source — аборт всей операции sync для этой кампании с ошибкой в UI (не частичное зеркало).
6. **Частичная ошибка копирования:** лог + итоговый счётчик (copied/deleted/failed); sync не считается успешным при failed>0 (результат возвращается вызывающему — связь с D.6).
7. **Защита от неверного CWD:** все цели — абсолютные; тест P4-02/T9 (одинаковость путей при CWD=корень и CWD=`frontend/map_editor`).
8. **Защита от выхода за корень:** `Path.resolve()` + `is_relative_to(root)` на каждую цель; symlink-цели отклоняются.
9. **Пользовательские данные:** `saves/{id}/campaign_state.json`, `saves/enigma_*.db`, `characters.json`, настройки — вне `locations/` → недостижимы для delete по построению (п.4).
10. **Перспектива (отдельный пункт P4-03):** продакшн-читателей у зеркал нет (B-17) — после стабилизации контракта зеркала объявляются deprecated (ADR), копирование отключается флагом, каталоги не удаляются автоматически.

### D.4. Контракт ресурсов

1. resource_id — rooted внутри `pixels/` (включая сегмент `текстуры/`), без абсолютных путей и `..` (R2 — без изменений).
2. Порядок разрешения: AssetStore (canonical) → `<id>` → `<id>.png` → `<id>.jpg` → `<id>.jpeg` → None (расширение probe — защитный слой; расширение в самом id разрешается шагом «как есть»).
3. Различаются три употребления: sprite sheet-кроп (`get_rect`), одиночное изображение (кроп на весь файл — валиден), портрет (та же цепочка резолвера, отдельная конфигурация `config/npc/individuals`).
4. Неразрешённая ссылка — не тихий fallback: warning в лог + (Фаза 9) запись в отчёт валидации редактора; fallback-рендер сохраняется (играбельность).
5. Один источник истины id: canonical = AssetStore; легаси-каталог — fallback. Синоним-слой запрещён.
6. Кэши: `SpriteRegistry` (двойной синглтон B-25 — унифицировать в Фазе 9), `_custom_sprites` — правила инвалидации см. D.8.

### D.5. Контракт готовности процессов

Состояния (единый словарь для backend/LLM/broker/редакторов): `NOT_STARTED`, `STARTING`, `READY`, `PORT_BUSY_FOREIGN`, `CRASHED_BEFORE_READY`, `EXITED_AFTER_READY`, `ALIVE_NOT_READY`.

| Правило | Содержание |
|---|---|
| G1 | Открытый порт ≠ готовность; 200 ≠ «наш процесс». Идентификация — handshake (модель: `protocol_version` broker'а, `client.py:42-51`); для backend добавляется версионный признак в health/status |
| G2 | Каждая ветка launcher'а различает `REUSE` (чужой готовый процесс, выбран осознанно) и `OURS_CRASHED` (мы спавнили, процесс умер) — два разных маркера, никаких общих `backend_proc is None` |
| G3 | Прогресс startup наружу: `/api/startup/status` (этап: импорт/миграции/схема/готово) + лог-события; launcher показывает этап, а не безлимитный спиннер |
| G4 | Тайм-ауты явные: pre-check окно ≥3×1с перед спавном; общий бюджет ожидания с классификацией и сообщением пользователю (причина + лог-файл + pid владельца через `_port_owner_pid`) |
| G5 | Никаких kill/освобождения портов, включая cleanup (kill-by-port :8000 удаляется/заменяется на диагностику — соответствие Уставу §19) |
| G6 | Редактор: падение инициализации — диагностичный экран/тост + безопасный выход редактора, не меню; in-process запуск — в try/except |

### D.6. Контракт редакторного сохранения

1. Единая точка: `CampaignManager.save_location/save_all_locations` возвращают `(bool, errors|count)`; `DataManager.save` возвращает `(bool, schema_errors)` (расширение типа возврата, обратно совместимо).
2. Все 5 call-site (B-18) обязаны использовать результат: успех/отказ/причина — в тосте; при отказе данные остаются в памяти с маркером «не сохранено» (виден в UI).
3. Centeral helper вместо пяти правок: `cm.persist(action_label)` → тост + лог + возврат результата.
4. Валидаторные schema-ошибки показываются списком (первые N), не только в logger.

### D.7. Контракт удаления локаций

Post-delete pipeline обязателен: unlink → удаление из `dm.locations` → (после D.3) sync с mirror-delete → пересборка compiled-реестра → инвалидация кэшей (D.8) → лог. Если sync/пересборка упали — удаление считается частичным, UI показывает, что осталось; повторное выполнение идемпотентно.

## Раздел F. Зависимости и порядок выполнения

### F.1. Граф порядка (почему так)

```
Ф0 (бэкапы/эталоны)
  → Ф1 (контракт W: ADR → конверсии → данные таверны → сейвы)
    → Ф2 (стартовая сцена: владелец чанков → наблюдаемость → пикинг → приёмка P1)
    → Ф3 (честный CRUD → валидатор → delete-пост-обработка → origin-драг)
      → Ф4 (sync: зеркало → тесты границы → судьба зеркал)
      → Ф5 (ресурсы: id → probe → merchant/назначения → валидатор id)
      → Ф6 (запуск: маскирование → идентификация → прогресс → редактор/§19)
        → Ф7 (мировое представление: интерьеры → зум → кэши)
          → Ф8 (CRUD из мира: create → delete/list → переходы)
          → Ф9 (Asset Library: импорт → единый реестр → метаданные → диагностика)
            → Ф10 (регресс → ADR/CI)
```

Обоснования отличий от RCA-1 §10:
1. **P1-02 (конверсии) ПЕРЕД P1-03 (данные)** — в RCA-1 порядок был обратный по смыслу (F1 данные → F2 код); прямое исполнение дало бы двойной origin. Контракт сначала, код потребителя вторым, данные третьими.
2. **P3-03 (delete-пост-обработка) после P4-01 (зеркальный sync)** — то же правило, что в RCA-1 («F6 до F5»), сохранено явно: иначе удаление работает по add-only семантике.
3. **Фазы 7–9 идут после ремонта** — World Editor требует мирового фрейма (Ф1), честного CRUD (Ф3) и валидатора; Asset Library требует диагностики ресурсов (Ф5) и единого реестра. Улучшения не подменяют ремонт (требование ТЗ-дополнения п.3): каждый пункт Ф7–Ф9 ссылается на устранённую им проблему.
4. **P2-01 после P1-03** — иначе эффект детерминированного владельца не проверяем на таверне (владелец границы и фрейм связаны, B-10).

### F.2. Правила параллелизации

- Независимые ветки после Ф3: Ф4, Ф5, Ф6 могут идти параллельно (разные файлы, разные тесты).
- Ф7 требует Ф3+P3-04; Ф8 требует Ф7; Ф9 требует P5-02; Ф10 требует всего.
- Любая параллельная работа фиксируется в журнале с указанием, какие пункты ведутся одновременно.
