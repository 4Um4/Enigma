# ENIGMA — LLM CONTRACT COMPLIANCE & MODEL EVALUATION

**Тип работы:** READ-ONLY исследование → аудит прежних испытаний → сравнительный benchmark → техническая рекомендация  
**Приоритет:** HIGH  
**Исполнитель:** технический исследователь / архитектор  
**Заказчик:** ENIGMA Game Designer  
**Объект:** локальные LLM, используемые и рассматриваемые для ENIGMA  
**Режим:** без изменений production-кода, конфигурации и действующей модели  
**Главный вопрос:** какая локальная модель лучше понимает и исполняет контракты ENIGMA, а не просто лучше пишет по-русски?

---

## 0. ОБЯЗАТЕЛЬНЫЕ ПРИНЦИПЫ

### 0.1. Главный критерий

**Понимание задачи и точное исполнение контракта важнее литературного качества русского языка.**

Приоритет критериев:

1. Понимание системных инструкций и контрактов.
2. Точное соблюдение обязательной структуры ответа.
3. Сохранение семантики входных данных.
4. Отсутствие выдуманных фактов и самовольных изменений.
5. Устойчивость на длинных и противоречивых инструкциях.
6. Способность работать с когнитивными задачами ENIGMA.
7. Русская речь, индивидуальность и литературное качество.
8. Скорость и потребление ресурсов.

Модель, провалившая обязательный контракт, не может компенсировать это красивой речью.

### 0.2. Запреты

- Не считать русскоязычную модель автоматически лучшей для ENIGMA.
- Не считать модель с большим количеством параметров автоматически более разумной.
- Не считать benchmark производителя доказательством качества на задачах ENIGMA.
- Не повторять прежние испытания без необходимости.
- Не подменять реальные результаты оценками из интернета.
- Не менять production-конфигурацию ради эксперимента.
- Не запускать несколько тяжёлых моделей одновременно.
- Не использовать платные API.
- Не менять действующую Hermes без отдельного решения заказчика.
- Не создавать новую систему метрик, если аналогичная уже существует.

### 0.3. Статусы доказательств

Каждое утверждение в отчёте маркировать:

- **VERIFIED** — подтверждено первичным результатом испытания, логом, конфигурацией или кодом.
- **PARTIALLY VERIFIED** — подтверждена только часть.
- **PROPOSED** — предложение исполнителя.
- **UNVERIFIED** — доказательств недостаточно.
- **ESTIMATE** — расчётная оценка.
- **REJECTED** — проверено и признано неподходящим.

# ЭТАП 2. АУДИТ ДЕЙСТВУЮЩЕГО КОНТРАКТА ENIGMA

**Цель:** определить, что именно модель обязана понимать и исполнять.

### 2.1. Изучить действующие инструкции

[ ] Найти системные промпты и контракты для LLM.

[ ] Найти контракты NPC dialogue.

[ ] Найти инструкции IntentCompressor.

[ ] Найти контракты BiographyDecomposer.

[ ] Найти extraction / normalization / structured output.

[ ] Найти GBNF-грамматики и схемы JSON.

[ ] Найти промпты когнитивных операций, если они уже реализованы.

[ ] Найти текущие правила валидации ответов.

[ ] Отделить обязательные требования от необязательных рекомендаций.

### 2.2. Составить контрактную карту

Для каждого типа задачи:

| Категория | Что модель должна делать | Что запрещено |
|---|---|---|
| Instruction following | Исполнять обязательные инструкции | Игнорировать пункты |
| Semantic interpretation | Сохранять исходный смысл | Подменять смысл |
| Structured output | Возвращать требуемую структуру | Пропускать поля |
| Extraction | Извлекать только подтверждённые факты | Выдумывать отсутствующие |
| Epistemics | Различать увиденное и услышанное | Приписывать знания |
| Biography | Сохранять временные и причинные связи | Терять важные сведения |
| Dialogue | Учитывать характер и ситуацию NPC | Игнорировать контекст |
| Reasoning | Следовать логике контракта | Самовольно менять правила |

### 2.3. Разделить ошибки

Обязательно различать:

- модель не поняла инструкцию;
- модель поняла инструкцию, но не соблюла формат;
- модель неверно интерпретировала входные данные;
- модель выдумала недостающие сведения;
- модель потеряла часть контекста;
- модель выполнила задачу, но нарушила запрет;
- модель дала корректный результат, но плохо выразила его по-русски.

Это разные классы отказов. Нельзя объединять их в одну оценку.

# ЭТАП 3. СОЗДАНИЕ КОНТРОЛЬНОГО КОРПУСА

**Цель:** получить воспроизводимый набор одинаковых заданий для всех моделей.

### 3.1. Источники

[ ] Использовать реальные контракты ENIGMA.

[ ] Использовать реальные ошибки моделей из этапа 1.

[ ] Использовать реальные игровые ситуации и данные NPC.

[ ] Не создавать искусственный benchmark, оторванный от задач игры.

### 3.2. Обязательные категории испытаний

**A. Точное исполнение инструкций**

[ ] Несколько обязательных требований одновременно.

[ ] Запреты, которые нельзя нарушать.

[ ] Инструкции с приоритетами.

[ ] Противоречивые входные данные, требующие корректного отказа или указания неопределённости.

**B. Контракт и структура**

[ ] Все обязательные поля присутствуют.

[ ] Типы значений соблюдены.

[ ] Неизвестные поля не выдумываются.

[ ] Лишние поля не добавляются, если запрещены.

[ ] JSON соответствует схеме.

[ ] GBNF и другие ограничения соблюдаются.

**C. Семантика**

[ ] Сохранение смысла исходного текста.

[ ] Различение факта, предположения и слуха.

[ ] Сохранение отрицаний.

[ ] Сохранение субъектов и объектов.

[ ] Сохранение временных отношений.

**D. Эпистемика**

[ ] NPC знает только то, что ему доступно.

[ ] NPC отличает собственное наблюдение от свидетельства.

[ ] NPC не получает знания из объективного состояния мира, если оно ему неизвестно.

[ ] NPC корректно работает с неопределённостью.

**E. Биография и память**

[ ] Извлечение фактов без потери важных деталей.

[ ] Сохранение временных связей.

[ ] Сохранение причинно-следственных отношений.

[ ] Отсутствие выдуманных биографических сведений.

**F. Когнитивные задачи**

[ ] Понимание мотивации NPC.

[ ] Согласование мысли, намерения и реплики.

[ ] Работа с противоречивой информацией.

[ ] Различение собственных убеждений NPC и убеждений других персонажей.

**G. Речь**

[ ] Узнаваемость голоса NPC.

[ ] Учет биографии и социального положения.

[ ] Естественная русская речь.

[ ] Отсутствие шаблонных ответов.

### 3.3. Golden Corpus

[ ] Для каждого задания записать ожидаемую семантику.

**Важно:** не оценивать модель по совпадению с единственной эталонной фразой. Оценивается соответствие контракту и смыслу.

# ЭТАП 5. СРАВНИТЕЛЬНЫЕ ИСПЫТАНИЯ

**Цель:** провести честное сравнение на одинаковых заданиях.

### 5.1. Замороженные условия

Для каждой модели фиксировать:

- точное имя модели;
- revision / источник;
- квантование;
- SHA256 файла GGUF;
- chat template;
- runtime и его версию;
- context size;
- temperature;
- top_p / top_k / min_p;
- repeat penalty;
- seed, если поддерживается;
- max_tokens;
- системный промпт;
- версию Golden Corpus.

Нельзя менять промпт специально под одну модель в основном сравнении.

Дополнительные оптимизации промпта допускаются только как отдельный эксперимент, с сохранением первоначального результата.

### 5.2. Повторяемость

[ ] Каждый тест выполнить минимум трижды там, где генерация стохастическая.

[ ] Для детерминированного extraction отдельно проверить temperature 0.

[ ] Сохранить полные входные данные и сырые ответы.

[ ] Не редактировать результаты вручную.

[ ] Повторить тесты, в которых обнаружено нестабильное поведение.

### 5.3. Измеряемые показатели

| Метрика | Что измеряет |
|---|---|
| Contract Pass Rate | Доля полностью исполненных контрактов |
| Critical Violation Rate | Частота критических нарушений |
| Required Field Accuracy | Точность обязательных полей |
| Semantic Preservation | Сохранение исходного смысла |
| Hallucination Rate | Выдуманные сведения |
| Instruction Retention | Сохранение требований длинной инструкции |
| Epistemic Accuracy | Корректность работы со знаниями |
| JSON / Schema Pass | Валидность структуры |
| Dialogue Coherence | Согласованность мысли и речи |
| Russian Quality | Качество русского языка |
| Latency p50 / p95 | Время выполнения |
| Peak VRAM / RAM | Пиковое потребление памяти |

### 5.4. Критические нарушения

Отдельно учитывать:

- пропуск обязательного поля;
- изменение смысла контракта;
- нарушение прямого запрета;
- выдумывание факта;
- выдачу неизвестного за известное;
- нарушение структуры, делающей результат непригодным для обработки.

Критическое нарушение не должно растворяться в среднем балле.

# ЭТАП 6. АППАРАТНЫЕ ИСПЫТАНИЯ

**Оборудование заказчика:**

- RTX 3070 Ti 8 GB;
- RAM 16 GB;
- Intel i7-9700F;
- DDR4-2666;
- локальный llama.cpp;
- текущий LLM endpoint `localhost:8181`;
- Host broker `localhost:8182`.

### 6.1. Проверки

[ ] Проверить загрузку модели.

[ ] Проверить доступный VRAM.

[ ] Проверить потребление RAM при загруженной игре.

[ ] Проверить prefill.

[ ] Проверить генерацию.

[ ] Проверить p50 и p95.

[ ] Проверить устойчивость на типовых промптах до 1.5k токенов.

[ ] Проверить контекст 16384, если модель и runtime поддерживают его.

[ ] Проверить работу игры одновременно с моделью.

[ ] Зафиксировать зависания, OOM и ошибки загрузки.

### 6.2. Критерии

- Типовая операция: p95 ≤ 10 секунд.
- Свободная RAM: достаточная для стабильной работы игры; для кандидатов с RAM-offload ориентир Blueprint — не менее 10 GB свободной RAM.
- Отсутствие деградации игрового процесса.
- Отсутствие необходимости в платном API.

Если модель не укладывается в ограничения оборудования, её можно оставить перспективным кандидатом, но нельзя рекомендовать как текущую рабочую замену.

### 6.3. Безопасность

[ ] Не запускать модели одновременно.

[ ] Не убивать процессы по имени.

[ ] Не обходить Host broker.

[ ] Не менять действующую модель в production.

[ ] Все испытания проводить в отдельном контролируемом режиме.

## 11. КРИТЕРИЙ УСПЕХА

Работа считается завершённой, когда заказчик получает ответ на один главный вопрос:

**Какая доступная локальная модель лучше всего исполняет реальные контракты ENIGMA, сохраняя семантику, эпистемическую корректность и когнитивную связность, и при этом способна работать на существующем оборудовании?**

Не «какая модель лучше говорит по-русски».

Не «какая модель больше».

Не «какая модель лидирует в чужом benchmark».

А какая модель действительно способна быть надёжным интеллектуальным исполнителем ENIGMA.

**До получения такого доказательства Hermes остаётся действующей контрольной моделью.**
