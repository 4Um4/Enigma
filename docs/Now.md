# ENIGMA — АКТУАЛЬНАЯ АРХИТЕКТУРА (FINAL SPEC v2.0)

## 0. ЦЕЛЬ И ОГРАНИЧЕНИЯ

Цель: Локальная RPG-система с NPC, демонстрирующими причинно-следственное поведение, устойчивостью реакций и предсказуемостью без детерминированности.

Жёсткие ограничения:
- LLM 7B–13B, VRAM ≤ 16GB, контекст ≤ 4k токенов
- Целевой масштаб: 10–30 NPC одновременно (max ~50)
- Локальный запуск без облачных API

---

## 1. КЛЮЧЕВОЙ ПРИНЦИП (НЕПРИКОСНОВЕНЕН)

**LLM НЕ ПРИНИМАЕТ РЕШЕНИЯ. НЕ МЕНЯЕТ СОСТОЯНИЕ. НЕ ВЫДАЁТ ДЕЛЬТЫ.**

LLM = слой вербализации (текст из чисел).
Python = слой интеллекта (DecisionHub).

NPC — система числовых сил (weights), не текстовых рассуждений.

  ### 2.1 ДЕРЕВО ЗАВИСИМОСТЕЙ (Data Flow & Logic)
    Эта схема показывает, как компоненты зависят друг от друга в рантайме.

    Уровни зависимости (сверху вниз):

    State Layer (NPCState / Personality): Ни от кого не зависит. Это "чистые данные", корень правды.

    Engine Layer (Break/Dice/Memory Engines): Зависит от State. Это чистые функции: получают данные → отдают дельты (изменения).

    DecisionHub: Зависит от Engines и Perception. Он вызывает движки, собирает их ответы в единый DecisionResult.

    StateApplicator: Зависит от DecisionHub. Он получает результат и записывает его обратно в State Layer.

    Примечание: Здесь мы исправляем баг из Now (2).md: логика слома воли вынесена в break_engine.py, аппликатор больше не "принимает решений".

    Verbalizer (LLM): Зависит от State и DecisionResult. Он просто "озвучивает" то, что уже произошло в системе.

  ### 2.2 КЛЮЧЕВЫЕ СВЯЗИ (МЕХАНИКИ)
    На основе анализа ваших файлов, я выделил три критических узла:

    Узел «Слом» (Break Cycle):
    NPCState.willpower + Event → break_engine.py → willpower_delta / identity_integrity_loss → StateApplicator.

    Узел «Память» (Memory Compression):
    L2 Event Memory → memory_engine.py (сжатие при достижении Tier-лимита) → L3 Identity Traits (обновление характера).

    Узел «Удача» (Resolution):
    DecisionHub (expected_success) → dice_engine.py (Stochastic shift ±10%) → Final Outcome.

    РЕЗЮМЕ АРХИТЕКТОРА:
    Система спроектирована так, чтобы LLM была полностью изолирована. Если завтра вы замените модель 7B на 13B, логика игры (веса, слом NPC, шансы на кубиках) не изменится ни на йоту. Это обеспечивает 100% предсказуемость архитектуры.

## 3. ИСТОЧНИКИ ПРАВДЫ

### 3.1 NPCState (динамический)
Единственный mutable объект. Содержит:
- `emotion`, `stress`, `intent`, `intent_duration`
- `relationship_cache` (snapshot из RelationshipStore)
- `active_traits` (наложения на личность, decay со временем)
- `trauma_markers` (set строк)
- `narrative_cache` (max 10 фактов, для EXPLAIN mode)
- `will_state` (free/coerced/broken/deceptive/loyal)

### 3.2 NPCPersonality (immutable)
Загружается из JSON один раз, never changes:
- `tier` (mass/minor/major) — статический уровень симуляции
- `drives_base` (control/significance/fear/desire, сумма=1.0)
- `willpower`, `breakpoint`, `loyalty_base`
- `voice_profile` (строка: "Говоришь грубо, материшься...") — для LLM
- `can_awaken` (bool) — разрешение на "пробуждение" через замену NPC

### 3.3 SceneState
Визуальное состояние:
- Координаты NPC (x,y)
- Объекты, препятствия
- НЕ источник логики, только для PerceptionFilter

## 4. MEMORY ARCHITECTURE (R1)

### 4.1 Core Memory = Weights (для логики)
- RelationshipStore: `trust/fear/debt` (-100..100)
- WorkingMemory: последние 20 событий с decay
- Используется DecisionHub для расчёта `relationship_modifier`

### 4.2 Narrative Memory = Facts (только для вербализации)
```python
@dataclass(frozen=True)
class NarrativeFact:
    event_type: str      # enum: "combat", "theft", "help"
    target_id: str
    emotion_tag: str
    day: int
    importance: float    # 0.0-1.0
```
**Ограничения:**
- Только 1 факт в обычном режиме (если importance > 0.6)
- Max 2 факта при `intent=EXPLAIN`
- НЕ используется в формуле `score()` — только для текста
- НЕТ semantic search, НЕТ retrieval по запросу игрока

---

## 5. DECISION HUB (R2) — ЯДРО ИНТЕЛЛЕКТА

### 5.1 Свойства
- Чистая функция, read-only, no LLM, no IO
- Seed per session (детерминизм ±10% randomness)

### 5.2 Формула score(action)
```python
score = (drive_weight × context_relevance)
      + emotion_modifier
      + relationship_modifier
      + trait_modifier
      - (fear × risk)
      + intent_inertia        # чем дольше intent, тем сложнее сменить
      ± noise(10%)
```

### 5.3 Trait System (вместо mutable personality)
- `active_traits`: накопленные черты (suspicious, grateful), decay к 0
- `personality_base`: неизменен
- Effective modifier = base + traits (traits затухают, base остаётся)

### 5.4 Explanation Mode
Explanation — не отдельный слой, а `intent=EXPLAIN` в DecisionHub.
- Выбирает top-2 NarrativeFacts
- Генерирует `VerbalizationContext` с `is_explain_mode=True`
- LLM получает факты и формулирует ответ "почему"

### 5.5 Risk Calculation
- Количество свидетелей
- Дистанция до события
- Видимые маркеры угрозы (heavy_armor, weapon) — НЕ реальная сила игрока

## 6. STATE APPLICATOR (R2.3)

Единственная точка записи в NPCState.

**Атомарность:** `copy.deepcopy` → изменения → замена целиком. При ошибке возвращается оригинал.

**Saturation (Diminishing Returns):**
- Изменения теряют эффективность у границ диапазона (headroom)
- Hard cap override при `intensity > 1.5` (критические события пробивают saturation)
- Curve: "soft" (linear) или "sigmoid" (S-образная)

**Применяет:**
- Дельты стресса/эмоций (с saturation)
- Обновления в RelationshipStore (atomic)
- Trait decay (к нулю каждый тик)
- Will break (при stress > breakpoint)

## 7. VERBALIZATION LAYER (R3)

### 7.1 Принципы
- Python генерирует ВСЮ фактуру (эмоция, нюанс, стиль)
- LLM только "оживляет" текстом
- **LLM не получает:** числа (stress=87), working_memory как текст, reasoning, дельты для применения

### 7.2 VerbalizationContext (frozen)
```python
npc_id, npc_name, tier
emotion, will_state, intent, intent_target
scene_hint: str (≤500 chars, факт из PerceptionFilter)
emotional_nuance: str (Python-generated: "зол, но сдерживается...")
speech_style: str (из dominant drive)
voice_profile: str (из Personality)
adult_content: bool
narrative_hints: Tuple[NarrativeFact, ...] (max 2)
is_explain_mode: bool
```

### 7.3 Tier-Aware Verbalization
- **MASS NPC:** Шаблоны без LLM (`"{name} бежит в панике}"`)
- **MINOR/MAJOR:** LLM с dynamic token budget
  - EXPLAIN: 300 токенов
  - TALK: 200 токенов
  - ATTACK/FLEE: 80 токенов
  - IDLE/OBSERVE: 0 токенов (lazy verbalization)

### 7.4 Lazy Verbalization
- **Радиус:** 10м для обычных действий, 15м для криков (WARN/ATTACK)
- Далёкие NPC не вызывают LLM (экономия VRAM)
- Только MASS-шаблоны или silence

### 7.5 Emotional Nuance Engine
Python генерирует литературное описание состояния из чисел:
- `stress > 70` + `angry` → "зол, едва сдерживается — голос на грани срыва"
- `trait suspicious > 0.6` → "недоверчиво прищуривается"
- `will_state=broken` → "сломлен — глаза бегают"

### 7.6 Контракт с LLM
**LLM получает:**
- Кто ты (voice_profile, speech_style)
- В каком состоянии (emotional_nuance, will_state)
- Что хочешь сделать (intent, target)
- Один важный факт (narrative_hints)
- Сцену (scene_hint)

**LLM НЕ возвращает:**
- `trust_delta`, `stress_delta` (игнорируются даже если есть в ответе)
- Новые intent (игнорируются)
- "Внутренние мысли" как логику (только как текст для F12 debug, генерируемый Python)

## 8. LIFE ENGINE (R4)

Фоновая симуляция:
- Движение (координаты в SceneState)
- Рутины (schedules)
- Физиология (голод, усталость → модификаторы к stress)
- Recovery (stress -= 5 за тик, 15 если sleeping)

**Не принимает решений.** Генерирует события для EventBus.

## 9. WORLD PRESSURE ENGINE

```python

```
NPC реагируют через DecisionHub как на обычные события.

## 10. NPC TIER SYSTEM (R1.7)

Статическое назначение при создании кампании:

**MASS (Tier 0):**
- Нет WorkingMemory (или ограниченная)
- Нет NarrativeFacts
- Шаблонная вербализация (без LLM)
- Упрощённый DecisionHub (только базовые реакции)

**MINOR (Tier 1):**
- Полный DecisionHub
- WorkingMemory (20 событий)
- Ограниченная NarrativeMemory
- LLM с короткими бюджетами

**MAJOR (Tier 2):**
- Полная симуляция
- LLM с длинными бюджетами (300 токенов для EXPLAIN)
- Может иметь `can_awaken=True`

**Запрещено:** Runtime upgrade tier. "Пробуждение" — через spawn нового NPC с загрузкой snapshot старого.

## 10.5 MEMORY ARCHITECTURE — ROADMAP (ДОПОЛНЕНИЕ К R1, R5, R10)
Текущая спецификация уже содержит Core Memory (веса, WorkingMemory, RelationshipStore) и NarrativeCache. Однако для долгосрочной памяти, позволяющей NPC ссылаться на события, произошедшие сотни часов назад, требуется трёхуровневая эволюция. Ниже описан пошаговый план внедрения, от простого к сложному, с сохранением совместимости с уже реализованными R1–R4.

📍 Уровень 0 — уже есть (R1, R4)
Числовые веса: отношения, страх, доверие, долг, активные черты, стресс.

WorkingMemory: последние 20 событий в виде структурированных записей (только для DecisionHub).

RelationshipStore: trust/fear/debt между NPC и игроком.

NarrativeCache: максимум 10 фактов для вербализации (explain mode).

Ограничение: через 20–30 событий старые факты вытесняются; NPC «забывает» важные поступки игрока.

📍 Уровень 1 — Долгосрочное хранение фактов (R5.1 – R5.3)
Шаг 1.1: Добавить LongTermFactStore
Цель: сохранять все значимые события навсегда (или до конца кампании) в структурированном, но не векторном виде.

Действия:

Создать таблицу SQLite: facts (id, npc_id, event_type, target_id, emotion_tag, day, importance, full_text, timestamp).

Каждый раз, когда ImportanceEngine вычисляет importance > 0.2, записывать факт в БД.

Для MASS NPC — не хранить (экономия).

Почему: без этого любой факт живёт только в WorkingMemory и NarrativeCache. SQLite даёт персистентность и возможность фильтрации (по дате, типу, участнику).

Шаг 1.2: Добавить clarity и confidence (R5.1)
Цель: модель памяти должна учитывать, насколько NPC был уверен в событии (видел своими глазами или ему рассказали) и как чётко помнит детали.

Действия:

В структуру факта добавить clarity: float 0.0-1.0 (выставляется PerceptionFilter: прямой взгляд → 0.9, слух за стеной → 0.4).

Добавить confidence: float (уменьшается с каждым игровым днём, например, умножается на 0.98 за день). Это естественное забывание.

В DecisionHub модификатор relationship_modifier умножается на clarity * confidence. Если NPC не уверен, что видел игрока за кражей — реакция слабее.

Почему: имитация человеческой памяти — события забываются, сомнения уменьшают влияние на логику.

Шаг 1.3: Добавить retrieval_by_filter (без векторов)
Цель: для вербализации извлекать из БД факты, соответствующие текущему контексту, без семантического поиска.

Действия:

В VerbalizationContext добавить параметры: target_id (с кем говорит), max_days_old (по умолчанию 30), event_types (например, только combat или theft).

При вызове LLM выполнить SQL-запрос:
SELECT full_text FROM facts WHERE npc_id = ? AND target_id = ? AND day >= ? AND importance > 0.4 ORDER BY day DESC LIMIT 3.

Результат подставить в промпт как «Ты помнишь: ...».

Почему: это RAG «на минималках» — без эмбеддингов, но уже даёт долгосрочную память. Достаточно для 80% случаев, когда важно время и тип события.

Когда готово: после этого NPC может помнить убийство брата спустя 100 часов игры.

📍 Уровень 2 — Семантический поиск (полноценный RAG)
Шаг 2.1: Внедрить эмбеддинги для фактов
Цель: находить события не только по прямым фильтрам (тип, участник), но и по смыслу. Например, игрок «унизил NPC» — это может быть записано как оскорбление, обман или публичный провал. LLM должна найти все похожие.

Действия:

Выбрать локальную эмбеддинг-модель (например, intfloat/e5-small-v2 — 300 МБ, работает на CPU).

Для каждого нового факта вычислять вектор и сохранять в FAISS или Chroma.

При вербализации формировать поисковый запрос из текущего intent и эмоции NPC (например, «предательство и гнев»), превращать его в вектор и искать 3–5 ближайших факта.

Результаты поиска добавлять в промпт.

Почему: фильтрация по типу события не всегда покрывает косвенные связи. Эмбеддинги позволяют NPC связывать разные события по смыслу, делая отклики богаче.

Шаг 2.2: Гибридный поиск (фильтры + вектор)
Цель: комбинировать точную фильтрацию (по участнику, дате) с семантическим поиском.

Действия:

Сначала отфильтровать факты по npc_id, target_id, min_importance, max_age.

На полученном подмножестве выполнить векторный поиск.

Результат — лучшее из двух миров.

Почему: чисто векторный поиск может найти событие с другим участником, что нерелевантно. Гибрид исключает это.

Шаг 2.3: Кэширование эмбеддингов и поиска
Цель: не пересчитывать эмбеддинги для каждого вызова LLM.

Действия:

Вычислять эмбеддинг факта один раз при сохранении.

Для частых поисковых запросов (например, «игрок, последние 5 дней») кэшировать результат на 1–2 секунды.

Почему: производительность — эмбеддинг на CPU занимает 20–50 мс, что при 50 вызовах LLM в минуту даст ощутимую задержку.

Когда готово: NPC получает способность «ассоциативно вспоминать» — важный шаг к реалистичности.

📍 Уровень 3 — Долгосрочное обучение и формирование черт (R5.4, R10.1)
Шаг 3.1: Детекция паттернов (ResonanceEngine)
Цель: если одни и те же типы событий повторяются, NPC должен менять свои стабильные черты характера (не только активные, но и базовые).

Действия:

ResonanceEngine анализирует LongTermFactStore каждые N действий (например, раз в 100 событий).

Ищет цепочки: betrayal_chain (игрок трижды предал доверие), chronic_help (постоянно помогает), gaslighting (игрок отрицает очевидное).

При обнаружении паттерна запускает to_identity_weight — постоянное изменение personality.drives_base (например, trust снижается на 0.05, fear растёт на 0.1).

Изменения сохраняются в профиль NPC и не сбрасываются.

Почему: без этого NPC не эволюционирует. Игрок может 100 раз предать — а NPC останется доверчивым. Паттерны делают мир динамичным и обучаемым.

Шаг 3.2: Долгосрочные цели и схемы (R10.4)
Цель: NPC может строить планы, основанные на многодневной памяти (например, отомстить через неделю).

Действия:

Добавить LongTermGoal: цель, статус, прогресс, крайний срок.

При каждом DecisionHub учитывать активные цели (увеличивать вес действий, ведущих к цели).

Вербализация может выдавать намёки: «Я ещё вернусь к этому разговору».

Почему: делает NPC проактивными, а не только реактивными.

📍 Уровень 4 — Иерархическая компрессия (опционально, для очень долгих кампаний)
Шаг 4.1: Сжатие старых фактов в «эпизодические резюме»
Цель: когда фактов становится десятки тысяч, поиск замедляется. Нужно агрегировать старые (более 100 игровых дней) в краткие обобщения.

Действия:

Раз в игровой месяц запускать фоновую задачу: выбирать факты старше 100 дней, группировать по типу и участнику.

LLM (или шаблон) генерирует сжатое описание: «В первый месяц ты трижды пытался меня ограбить».

Старые факты удалять, оставляя только агрегат.

Почему: баланс между полнотой и производительностью.

# ENIGMA — MASTER ROADMAP & ARCHITECTURE (v4.0)
**Тип проекта:** Хардкорная RPG-симуляция (Iron-man)
**Главный принцип:** Недопустимость упрощений. Это не базовая инди-игра, а сложнейший причинно-следственный стек (Causal Stack), где каждая переменная имеет вес, а ошибки архитектуры ведут к каскадному обрушению логики мира. 
LLM — это исключительно голос. Python — это интеллект.

---

## ГЛОБАЛЬНАЯ ЦЕПЬ ПРИЧИННОСТИ (DATA FLOW)
Событие не может перескочить слой. Любое действие в игре проходит строгий конвейер:

1. **Event** (Ввод игрока / Тик мира)
2. **Spatial Filter** [L1] (Кто видит? Геометрия сцены)
3. **DecisionHub** [L0] (Ядро вычислений: профиль + память + эмоции - страх)
4. **Resolution** [L2] (Бросок кубиков и стохастическое смещение)
5. **State Update** [L0 + L5] (Запись дельт, травм, сдвигов памяти)
6. **World Influence** [L6] (Реакция макро-мира, продвижение фронтов)
7. **Verbalization** [L0] (LLM получает `intent` и озвучивает результат)

---

## АРХИТЕКТУРНЫЙ СТЕК (СЛОИ СИСТЕМЫ)

### L0 — FOUNDATION (БАЗОВЫЙ ФУНДАМЕНТ)
* **R1 Memory Core (История → Числа):** Перевод фактов в веса. `EventMemory` (сжатие и деградация), `ResonanceEngine` (поиск паттернов). `NarrativeFacts` (замороженные факты). *Критично: Память только формирует веса, решения принимает Хаб.*
* **R2 Decision Core (Причинность):** `DecisionHub` — единственная точка принятия решений. Считает `score(action)` на основе эмоций, отношений, черт (`traits`) и рисков.
* **R3 Verbalization Layer (Речь):** Получает только `intent`, `emotion` и контекст. LLM не видит цифр.

### L0.5 — ПЕРСИСТЕНТНОСТЬ (IRON-MAN БАЗА ДАННЫХ)
* **R1.8 Strict Persistence Engine:** Никаких слотов сохранений. `Auto-save` строго при смене локации или выходе.
* **Защита от Save Scumming:** Игрок не может откатить состояние.
* **Награда (Inspiration):** Токен переброса кубика выдается только за `Critical Success` в сложных заявках.

### L1 — ПРОСТРАНСТВО (ГЕОМЕТРИЯ)
* **R4 Spatial System:** Граф локаций (`LocationGraph`) и координаты (`LocalSpace`). Зона видимости (`Line-of-sight`) и срез доступных действий (`Scene Extraction`).

### L2 — МЕХАНИКА ИСХОДОВ (НЕОПРЕДЕЛЕННОСТЬ)
* **R5 Resolution Layer:** `expected_success` от Хаба смещается броском кубика. 
* **Gap System:** Разница между ожиданием и реальностью (`actual - expected`) порождает травмы и новые черты характера.

### L3 & L3.5 — АВАТАР ИГРОКА И ОГРАНИЧЕНИЯ
* **R6 Character Constraint:** Профиль игрока определяет `affinity` к действиям. 
* **R6.4 Ego Resistance:** Персонаж может сопротивляться вводу игрока, если действие противоречит его `traits` (бросок воли персонажа против игрока).
* **R6.5 Hardcore Death:** При 0 HP → `Unconscious`. Три провала Death Saves (<50% или 1 на D20) = `Permadeath`. Конец игры.

### L4 — СОЦИАЛЬНАЯ СЕТЬ
* **R7 Social System:** `RelationshipMatrix` (NPC↔NPC). Распространение слухов по графу связей.

### L5 — СЛОМ (ПОВЕДЕНЧЕСКАЯ ДЕГРАДАЦИЯ)
* **R8 Break System:** Накопление давления (`fear + stress + failures - support`). Приводит к потере `identity_integrity` и переходу к маскам (`FAKE_SUBMISSION`, `BETRAYAL`). 

### L6 — МИР (ДАВЛЕНИЕ СВЕРХУ)
* **R9 World Director:** Глобальное состояние (`danger_level`, `scarcity`). Фракции и фронты развиваются автономно.
* **R9.8 Real Economy:** Цены = `Base * Regional_Scarcity * NPC_Trust`.

### L8.5 — GAME LOOP (ВРЕМЯ И ЦЕЛИ)
* **R13 Tick-Based Engine:** Асинхронное время. Диалог = 1 тик. Перемещение/Отдых = X тиков.
* **Campaign Manager:** Сюжет длится месяцы внутриигрового времени. Мир меняется асинхронно во время длительного отдыха (анимация времени).

### L9 — FRONTEND & UX (ABSOLUTE FOG OF WAR)
* **R14.1 Эволюция UI:** Текст → Диалоговые окна (Persona style) → 2D Карта с фишками → Единый UI.
* **R14.2 Гибридный ввод:** Выбор из списка ИЛИ `free text` (парсер конвертирует в `PlayerIntent`).
* **R14.3 Absolute Fog of War:** Игрок видит только свои статы. Цифры NPC скрыты (заменены дрожанием текста, цветом портрета). Имена скрыты (???), пока NPC не представится. Карта скрыта в темноте/при слепоте.
* **R14.4 Иллюзия D20:** Математика [0..100] выводится в UI как бросок D20 (1-20).
* **R14.5 Latency Masking:** Анимация «NPC думает...» скрывает задержку LLM (2-4 сек).

### L10 — DEVTOOLS (ЦЕНТР УПРАВЛЕНИЯ ПОЛЕТАМИ)
* **R15.1 God Mode Console:** Скрытая консоль (`~`) для разработчика. Показывает сырые веса и матрицу.
* **R15.2 Central Math Config:** Единый файл конфигурации всех формул и весов для защиты от хардкода.

## РЕЕСТР КРИТИЧЕСКИХ ОШИБОК И УЯЗВИМОСТЕЙ (КОНТЕКСТ АРХИТЕКТУРЫ)
*Система требует постоянного удержания контекста слабых мест. Игнорирование этих пунктов ломает фундаментальный опыт игры.*

1. **Утечка логики в StateApplicator (или другие "тупые" модули)**
   * *Где находится:* Запись состояния NPC.
   * *Как исправить:* Вынести все константы (например, порог слома = 80) в `Central Math Config` (R15.2). Аппликатор должен получать готовую дельту из Хаба.
   * *Зачем исправлять (Что ломает):* Нарушает изоляцию. Система записи начинает принимать сложнейшие психоэмоциональные решения, делая архитектуру непредсказуемой.

2. **Пробой Fog of War через LLM**
   * *Где находится:* Слой вербализации (R3).
   * *Как исправить:* Жестко фильтровать промпты. LLM не должна получать точные значения `stress` или скрытые мотивы, только `intent` и эмоциональный фон.
   * *Зачем исправлять (Что ломает):* Уничтожает ощущение загадки. NPC начнет говорить: "Мой уровень стресса 85, я сдаюсь", превращая глубокую симуляцию в дешевую табличку.

3. **Отсутствие Gap System (Безболезненные кубики)**
   * *Где находится:* Resolution Layer (R5).
   * *Как исправить:* Обязательно вычислять `actual_outcome - expected_success`.
   * *Зачем исправлять (Что ломает):* Без разницы между ожиданием и реальностью NPC и игрок не получают травм и сдвигов характера. Игра становится линейной, исчезает "рост через боль".

4. **Игнорирование Ego Resistance игрока**
   * *Где находится:* Слой действий игрока (R6.4).
   * *Как исправить:* Сверка намерения (`intent`) с профилем игрока перед отправкой в Хаб.
   * *Зачем исправлять (Что ломает):* Если игрок может менять поведение как перчатки без штрафов воли, игра становится тупой песочницей, а не отыгрышем. Теряется вес выбранной роли.

5. **Замораживание мира без игрока**
   * *Где находится:* World Director (R9).
   * *Как исправить:* Принудительный прогон тиков макро-событий во время отдыха игрока.
   * *Зачем исправлять (Что ломает):* Мир кажется "мертвой декорацией", ждущей героя. Отсутствие давления сверху лишает кампанию драйва и реализма.



🔍 Как ENIGMA оценивает произвольное действие игрока
1. Intent Parser (rule-based, patterns/)
Задача: быстро определить, что игрок пытается сделать (атака, диалог, перемещение, взаимодействие с объектом, вандализм).

Как работает: YAML-шаблоны с ключевыми словами и регулярными выражениями.

Пример:
"обассать стену" → ключевое слово "ссать" → парсер определяет как action_type = "vandalism", target = "wall".
"отрубить голову трупу" → "отрубить" + "голову" + "трупу" → action_type = "dismember", target = "corpse".

Если действие не распознаётся ни одним паттерном — оно отправляется в fallback-обработчик (LLM или DM как «судья»).

2. DM Router (Этап 1 из DM System)
Получает PlayerIntent от парсера.

Проверяет синтаксическую корректность (есть ли цель? есть ли субъект?).

Если парсер не смог разобрать — вызывает LLM для уточнения: «Игрок сказал "...", что это значит?» (редко, но возможно).

3. DM Validator (Этап 3 — «Фильтр реальности»)
Самый важный слой. Проверяет, возможно ли действие в текущем контексте.

Что проверяет:

Есть ли цель? (стена существует, труп есть в сцене)

Досягаемость? (игрок рядом со стеной?)

Физическая возможность? (отрубить голову трупу — можно, если у игрока есть оружие; обоссать стену — можно всегда)

Социальные ограничения? (при свидетелях — последствия)

Результат: is_possible = True/False, difficulty (DC), risk (заметят ли).

Если действие невозможно — DM возвращает игроку объяснение: «Вы не можете отрубить голову трупу, потому что у вас нет острого оружия».

4. Resolution Layer (R5, D&D 5e ядро)
Если действие возможно — отправляется в action_resolver.py.

Для каждого типа действия есть своя механика:

Атака/расчленение: бросок D20 + модификаторы (сила, оружие) против СЛ (сложности). Успех → изменение состояния цели (труп становится «обезглавленным»).

Вандализм (обоссать стену): проверка скрытности (если свидетели) + влияние на репутацию. Успех → объект получает флаг soiled, NPC могут отреагировать отвращением.

Градиент результата: крит.провал, провал, успех, крит.успех. Например, при крит.успехе обсирания стены — NPC могут начать рвать или убежать.

5. Decision Hub NPC (R2)
Каждый NPC в радиусе получает событие: «игрок совершил действие X с результатом Y».

На основе своих весов (personality, trust, fear, emotion, stress) вычисляет score для реакций: атаковать, убежать, вызвать стражу, заорать, игнорировать.

Пример: Торнин (трактирщик) при виде игрока, мочащегося на стену, получит score(ATTACK) = 0.8 (если у него черта «чистоплюй»), score(FLEE) = 0.2.

6. DM Aggregator (Этап 8)
Собирает все реакции NPC и результат действия в единое нарративное описание.

LLM (DM) генерирует связный текст: «Вы отрубаете голову трупу. Торнин в ужасе кричит: "Вы сумасшедший!" и выбегает на улицу. Люся падает в обморок.»

Важно: LLM не придумывает новые факты (голова отрублена — это уже в scene_state), а только описывает.

🧪 А что если действие вообще не подходит ни под один тип?
Пример: игрок пишет «Я превращаюсь в дракона и улетаю».

DM Validator проверит: есть ли у игрока способность превращаться? (по умолчанию — нет, если не заклинание).
→ is_possible = False.

DM вернёт: «Вы не можете превратиться в дракона. У вас нет такой магии.»

Пример: «Я говорю стене "привет"»

Парсер распознаёт talk, цель — wall. Валидатор: стена не может ответить, но действие болтовни возможно.

DM описывает: «Вы говорите стене "привет". Она молчит. NPC смотрят на вас с недоумением.»

🎭 Абсурд и жестокость — это поощряется?
ENIGMA не оценивает мораль, только последствия. Если игрок хочет ужасов — система симулирует реакцию мира: стражи, репутация, психологические травмы у NPC. Но технически любое действие обрабатывается одинаково.

Более того, ваша архитектура специально спроектирована для неограниченной свободы:

Нет предопределённого списка действий.

Нет жёстких запретов (кроме физической невозможности).

Есть только правила разрешения и симуляция последствий.
