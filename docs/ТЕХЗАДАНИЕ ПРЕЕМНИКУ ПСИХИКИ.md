Что уже работает:
  • TickOrchestrator (фазовый GameLoop, 5 фаз)
  • EventCompiler → ProjectionEngine → WorldSnapshot (начало TRC)
  • SpatialRegistry (single spatial authority, ADR-048)
  • DecisionHub (evaluator, не диктатор)

Чего нет (и не нужно сейчас):
  • Sex system
  • Books / knowledge system
  • Magic system
  • Learning system (вне identity/drive)
  • LLM expansion (только ограничение)

4. СПИРАЛЬНЫЙ ПЛАН (4 фазы + 0-фаза стабилизации)
═══════════════════════════════════════════════════════════════════════════════

ПРИНЦИП: Не строим сначала TRC, потом society.

┌─────────────────────────────────────────────────────────────────────────────┐
│ ФАЗА 0: СТАБИЛИЗАЦИЯ ОНТОЛОГИИ (TRC v1.0)                                  │
│ Период: 1-2 недели                                                          │
│ Цель: Завершить начатое в V.0.5.3.1.7                                       │
└─────────────────────────────────────────────────────────────────────────────┘

Что делать:
  1. CommitGate — единая точка записи state
     • Все домены пишут ТОЛЬКО через CommitGate
     • CommitGate валидирует: нет конфликтов, нет дублей
     • CommitGate генерирует WorldSnapshot (immutable)

  2. CausalValidator — проверка причинности на выходе тика
     • Проверяет: все события имеют cause → effect цепочку
     • Проверяет: нет orphaned effects (эффект без причины)
     • Проверяет: нет causal loops (A → B → A в одном тике)

  3. State unification — убрать dual-state
     • dict state → deprecated (миграция)
     • dataclass state → runtime canonical
     • snapshot state → read-only projection (CommitGate output)

  4. Frontend authority fix
     • Frontend spatial compiler → pure consumer
     • Frontend читает WorldSnapshot, не пишет в SpatialRegistry
     • Ghost Position Interpolation → решён через WorldSnapshot lag

Что НЕ трогать:
  • Сами домены (Spatial, Social, Physiology, Identity)
  • LLM (только ограничить: не писать в state)
  • DecisionHub (оставить evaluator)
  • WillpowerGate (оставить интегратор)

Риски:
  • CommitGate может стать bottleneck (профилировать)
  • Миграция dict → dataclass — сломать старые тесты
  • Frontend refactor — визуальные артефакты

Метрики на выходе:
  • Repository Hygiene ≥ 0.85
  • Ownership Clarity ≥ 0.80
  • 0 dual-state фактов (audit)

┌─────────────────────────────────────────────────────────────────────────────┐
│ ФАЗА 1: AGENT INTERFACE CONTRACT (AIC)                                    │
│ Период: 2-3 недели                                                          │
│ Цель: Unified Agent Interface Layer над доменами                            │
└─────────────────────────────────────────────────────────────────────────────┘

Что делать:
  1. Agent API — единый интерфейс для всех акторов
     • NPCState, AvatarState, EventActor → unified AgentState
     • AgentState = read-only view для доменов
     • AgentState = write-through для CommitGate

  2. Domain → Agent API → CommitGate pipeline
     • Spatial Domain пишет через Agent API.Spatial.write()
     • Social Domain пишет через Agent API.Social.write()
     • Physiology Domain пишет через Agent API.Body.write()
     • Identity Domain пишет через Agent API.Identity.write()
     • Agent API → CommitGate → State

  3. DecisionHub refactor — читает Agent API, не state напрямую
     • DecisionHub → Agent API.read() → решение
     • DecisionHub → Agent API.write(intent) → CommitGate

  4. Agent Interface Contract (файл/ADR)
     • Определить: что домен может читать/писать
     • Определить: порядок доменов в тике (Spatial → Social → Identity?)
     • Определить: conflict resolution между доменами

Что НЕ трогать:
  • Логика доменов (оставить как есть)
  • L1 Chronicle (факты остаются фактами)
  • PerceptualKernel (восприятие остаётся локальным)
  • SocialPropagation (граф остаётся)

Риски:
  • God-agent anti-pattern (контролировать: Agent API = thin layer)
  • Performance: O(N × domains) → оптимизировать через batch writes
  • DecisionHub refactor → регрессия в решениях

Метрики на выходе:
  • Ownership Clarity ≥ 0.85
  • Causal Integrity ≥ 0.85
  • 0 прямых записей в state из доменов

┌─────────────────────────────────────────────────────────────────────────────┐
│ ФАЗА 2: BELIEF LAYER (локальная эпистемология)                              │
│ Период: 2-3 недели                                                          │
│ Цель: NPC может ошибаться, сомневаться, иметь устойчивую ложную картину     │
└─────────────────────────────────────────────────────────────────────────────┘

Что делать:
  1. Belief — структура убеждения
     • belief_id, subject, predicate, confidence (0.0-1.0)
     • evidence: List[Evidence] (почему я так думаю)
     • contradictions: List[Fact] (факты против)
     • last_updated: tick_id
     • source_trust: Dict[source_id, float]

  2. Evidence — структура доказательства
     • type: PERCEPTUAL / SOCIAL / INFERRED
     • source: who/what provided this
     • strength: 0.0-1.0
     • recency: tick_delta

  3. BeliefRevision — пересмотр убеждений
     • Новый факт противоречит belief? → confidence -= delta
     • confidence < threshold? → belief помечается UNSTABLE
     • Новое evidence подтверждает? → confidence += delta
     • recency decay: старое evidence слабеет

  4. PerceptualKernel → Belief (не прямо в L1)
     • PerceptualEvidence → BeliefRevision → Belief
     • L1 Chronicle = факты (objective)
     • Belief = интерпретация (subjective)

  5. DecisionHub читает Belief, не только L1
     • DecisionHub → Agent API.Belief.read() → решение
     • NPC действует на основе своей модели мира, не фактов

Что НЕ трогать:
  • L1 Chronicle (факты остаются каноническими)
  • PerceptualKernel (восприятие остаётся локальным)
  • CFRM (локальные поля остаются)

Риски:
  • Belief explosion: N NPC × M beliefs = O(N×M) памяти
    → решение: belief pruning (confidence < 0.1 → archive)
  • DecisionHub регрессия: чтение belief медленнее, чем L1
    → решение: belief cache + lazy update
  • Player confusion: NPC действует "неправильно" (по ложному belief)
    → это фича, не баг

Метрики на выходе:
  • NPC может иметь устойчивое ложное убеждение (50+ тиков)
  • Causal Integrity ≥ 0.88
  • The Fool Playability ≥ 0.82

┌─────────────────────────────────────────────────────────────────────────────┐
│ ФАЗА 3: SOCIAL PROPAGATION v2 (искажение и доверие)                         │
│ Период: 2-3 недели                                                          │
│ Цель: Информация искажается при передаче, эмерджентность через слухи        │
└─────────────────────────────────────────────────────────────────────────────┘

Что делать:
  1. Source Trust — доверие к источнику
     • relationship_cache[source] → trust_score
     • trust_score влияет на acceptance нового evidence
     • low trust → evidence игнорируется или помечается SUSPECT

  2. Information Distortion — искажение при передаче
     • A говорит B: "игрок убил X"
     • B: PerceptualKernel оценивает источник (доверие к A?)
     • B: BeliefRevision — обновляет belief с confidence = trust × original_confidence
     • B говорит C: confidence снижается, детали теряются
     • C: получает "кто-то что-то сделал игроку" (distorted)

  3. Social Propagation refactor
     • Сейчас: передаёт факты (objective)
     • Новое: передаёт beliefs (subjective) + source metadata
     • Propagation strength = relationship_strength × trust × urgency

  4. Cultural Norm Propagation (начало)
     • Norm = shared belief с высокой confidence в группе
     • Norm propagation: если 3+ NPC в группе имеют belief X → norm emerges
     • Norm pressure: NPC с противоположным belief получает social pressure

Что НЕ трогать:
  • L1 Chronicle (факты остаются)
  • Belief Layer (используем, не меняем)
  • Social graph (оставляем)

Риски:
  • Echo chamber: группа NPC усиливает друг друга → нереалистичные norms
    → решение: external event injection (игрок, мир) ломает echo chambers
  • Performance: propagation каждый тик → O(N²)
    → решение: propagation batch, не каждый тик
  • Player frustration: слухи "неправильные" → невозможно отследить
    → решение: causal observatory показывает propagation chain

Метрики на выходе:
  • Информация искажается при передаче (measurable distortion)
  • Cultural norm emergence (3+ NPC → shared belief)
  • Causal Integrity ≥ 0.90
  • The Fool Playability ≥ 0.85

┌─────────────────────────────────────────────────────────────────────────────┐
│ ФАЗА 4: EMERGENT GOAL GENERATION (порождение целей)                       │
│ Период: 3-4 недели                                                          │
│ Цель: NPC порождает новые цели из конфликта, не только реагирует          │
└─────────────────────────────────────────────────────────────────────────────┘

Что делать:
  1. Drive Conflict Detection
     • Два драйва конфликтуют: duty vs fear, trust vs anger
     • Conflict intensity = min(drive_a, drive_b) × opposition
     • Conflict duration: сколько тиков конфликт длится

  2. Emergent Goal Generator
     • Конфликт intensity > threshold → generate new goal
     • Goal = resolution strategy (не заданная разработчиком)
     • Примеры:
       - duty(0.9) + fear(0.8) → goal: "найти компромисс" (не COMPLY/RESIST)
       - trust(0.7) + anger(0.6) → goal: "проверить источник гнева"
       - identity("guard") + body(pain=0.8) → goal: "найти замену"

  3. Viability Pre-Generation Gate расширяется
     • Сейчас: исключает невозможное (ROUTINE при threat > 0.3)
     • Новое: включает emergent goals в пространство возможностей
     • Goal viability = spatial_possible × body_possible × social_possible

  4. WillpowerGate — оставляем интегратором
     • WillpowerGate не меняем (инерция воли сохраняется)
     • Emergent goal проходит через WillpowerGate как любой другой intent
     • Результат: COMPLY / CONDITIONED / RESIST / DEFY / EMERGENT

  5. Goal Lifecycle
     • Goal created → active → pursued → achieved / failed / abandoned
     • Goal abandonment: если conflict resolved другим путём
     • Goal memory: achieved goals → L1 Chronicle ("я нашёл компромисс")

Что НЕ трогать:
  • WillpowerGate (инерция сохраняется)
  • DecisionHub (evaluator, не диктатор)
  • Viability Gate (только расширить)

Риски:
  • Goal explosion: NPC генерирует слишком много goals
    → решение: max_active_goals = 3, pruning по priority
  • Unpredictable behavior: NPC делает "странное"
    → это фича, но нужен causal observatory для отладки
  • Performance: goal generation каждый тик → expensive
    → решение: generate только при conflict detection, не каждый тик

Метрики на выходе:
  • NPC порождает новую цель из конфликта (не заданную)
  • Самая длинная причинная цепочка ≥ 15 звеньев
  • The Fool Playability ≥ 0.85
  • Causal Integrity ≥ 0.90

7. РИСКИ И МИТИГАЦИЯ
═══════════════════════════════════════════════════════════════════════════════

Риск 1: Переписывание всего под единую агентную модель
  Митигация: Agent API = thin layer, не переписывание. Домены остаются.

Риск 2: God-agent anti-pattern
  Митигация: Agent API = read-only view + write-through. Нет логики внутри.

Риск 3: Performance degradation (O(N × M) beliefs)
  Митигация: belief pruning, batch propagation, lazy update.

Риск 4: Frontend regression
  Митигация: Frontend = pure consumer с самого начала. Нет write authority.

Риск 5: LLM откат в script-first
  Митигация: LLM ограничен VerbalizationContext. Нет write в state.

Риск 6: Сложность выше управляемости (1 человек)
  Митигация: фазы ≤ 3 недель. DNA-метрики каждую неделю. Регрессия → откат.

9. ВЕРДИКТ ПО СОВЕТУ (единая агентная модель + модульные домены)
═══════════════════════════════════════════════════════════════════════════════

Оценка: 80% верен, 20% требует коррекции

✔ Верно:
  • Диагноз: нет Agent Interface Contract
  • Диагноз: домены пишут в разные состояния
  • Диагноз: multi-writer chaos, dual truth
  • Решение: Unified Agent Interface Layer (не переписывание)
  • Модульные домены — уже сильная сторона, не проблема

⚠ Требует коррекции:
  • Не упоминает TRC (Tick Reality Contract) — критично
  • Не упоминает CommitGate / CausalValidator
  • Не упоминает Frontend authority problem
  • Не упоминает Belief Layer (критично для твоих критериев)
  • "60% правильно, 40% опасно" — переосторожно. Риски управляемы.

❌ Неверно:
  • "не трогать LLM" — LLM нужно ограничивать, не игнорировать
  • "сделать одного агента" — нет, сделать Agent API над доменами

Итог: совет — хорошая отправная точка, но неполный.
       Это ТЗ дополняет его TRC, CommitGate, Belief Layer, Emergent Goals.
