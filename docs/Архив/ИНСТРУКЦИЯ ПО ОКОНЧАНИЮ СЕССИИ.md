# ИНСТРУКЦИЯ ПО ОКОНЧАНИЮ СЕССИИ (Спринта)

> **Назначение:** Этот файл — чеклист для LLM-архитектора. После каждого спринта ОБЯЗАТЕЛЬНО обновить документы проекта.
> Без них ИИ в новой сессии будет слеп — `MUTATIONS.md` даёт историю, но не понимание.

---

## §0. КРИТИЧЕСКИЕ ПРАВИЛА (читать ПЕРВЫМ)

### Правило 1: Читай файлы ЦЕЛИКОМ, не последние 30 строк

**ЗАПРЕЩЕНО** читать файл через `Get-Content | Select-Object -Index (N..M)` или `tail -30` перед редактированием.

**Почему:** LLM читает последние 30 строк, видит хвост документа, не видит структуру, не видит начало секции — и в итоге вставляет свой блок не в то место, ломая нумерацию, дублируя заголовки, разбивая таблицы. Именно так были сломаны ADR (5 однострочных записей), MUTATIONS (дублирующая нумерация 33-36), DTO Registry (слитый S-93 блок), РЕЖИМ РАБОТЫ (два раздела 3.7).

**Обязательно:**
1. Прочитать файл **целиком** — `Get-Content path/to/file.md` или `cat path/to/file.md`.
2. Понять структуру — какие секции есть, какая нумерация, где заканчивается каждый блок.
3. Найти точное место вставки по контексту.
4. Только потом предлагать `БЫЛО`/`СТАЛО`.

**Исключение:** Файлы длиннее 2000 строк — читать по частям, но ОБЯЗАТЕЛЬНО все части, от начала до конца.

### Правило 2: Один файл за итерацию

**ЗАПРЕЩЕНО** предлагать изменения в 3-5 файлов одновременно в одном ответе.

**Почему:** При параллельной правке нескольких файлов LLM теряет контекст, путает БЫЛО/СТАЛО между файлами, вставляет блок из файла A в файл B. Результат — сломанные документы.

**Обязательно:**
1. Одна итерация = один файл.
2. Прочитал файл целиком → предложил БЫЛО/СТАЛО для этого файла → ждём подтверждения → следующий файл.
3. Если нужно обновить 5 файлов — это 5 итераций, не одна.

### Правило 3: Сначала найди расположение файлов

**ЗАПРЕЩЕНО** гадать пути к файлам.

**Обязательно ПЕРЕД любым обновлением:**
```powershell
# Найти все .md в docs/
Get-ChildItem -Path "docs/" -Filter "*.md" -Recurse | Select-Object FullName

# Найти конкретный файл по имени
Get-ChildItem -Path "docs/" -Filter "*ADR*" -Recurse | Select-Object FullName

# Найти architecture/*.yaml
Get-ChildItem -Path "architecture/" -Filter "*.yaml" -Recurse | Select-Object FullName
```

Только после того, как пути подтверждены — начинать чтение и редактирование.

### Правило 4: Археология ПЕРЕД предложениями (параллельная работа)

LLM-архитекторы работают параллельно. Их память устаревает. **Любое предложение без предварительной археологии = баг.**

**ФАЗА 1 — АРХЕОЛОГИЯ (читать, не писать):**
1. Прочитать `MUTATIONS.md` целиком — что сделали другие.
2. Прочитать `ADR` целиком — какие новые ограничения.
3. Прочитать `DTO Registry` целиком — какие контракты изменились.
4. Прочитать `reports/LAST_SESSION.md` — красные инварианты.
5. Прочитать целевой файл(ы) целиком — текущее состояние.

**ФАЗА 2 — ПРЕДЛОЖЕНИЯ (писать, не читать):**
Только после ФАЗЫ 1 — предлагать БЫЛО/СТАЛО.

**ЗАПРЕЩЕНО:** Предлагать изменения на основе памяти из прошлой сессии. Только живая верификация.

### Правило 5: Вставка по контексту, не в конец/начало

**ЗАПРЕЩЕНО** добавлять блок в конец файла или в начало, если он логически принадлежит середине.

**Обязательно:**
- Найти секцию, к которой относится изменение (например, `## DOM-04: SPATIAL & LOCOMOTION`).
- Найти последнее вхождение в этой секции.
- Вставить ПОСЛЕ него, ДО следующего `---` или `## `.
- Проверить нумерацию (если добавляешь запрет №37, предыдущий должен быть №36).
- Проверить code fences (открыл ` ``` ` — закрыл ` ``` `).

## §1. Чеклист (5 пунктов)

### 1. `MUTATIONS.md` — ЧТО произошло

**Файл:** `docs/MUTATIONS.md`

**Формат:**
```
- 🔵 **S##** Название ADR или задачи. Описание изменения (что добавлено/удалено).
  Files: путь/к/файлу.py
```

**Пример:**
```
- 🟢 **S116** BUG-N4: Timestamp-mismatch убил Speech Bubbles. task_scheduler.py:131 теперь пишет time.time() (wall-clock), game_loop/__init__.py:557,891 читает time.time(). Разница устранена.
  Files: backend/app/services/game_loop/task_scheduler.py, backend/app/services/game_loop/__init__.py
```

**Правила:**
- Сначала прочитать `MUTATIONS.md` целиком — найти последнюю сессию `S##`.
- Номер сессии = `max(существующие) + 1`.
- Вставить в соответствующий DOM-раздел (DOM-01..DOM-11).
- Если DOM-раздела нет — создать в порядке DOM-01 → DOM-11.

---

### 2. `ADR` — ПОЧЕМУ принято решение

**Файл:** `docs/ADR (Architecture Decision Records).md`

`ADR-XXX` [TYPE] **Title** — Essence (1 line)
  Taboo: ❌ ... (опционально)
  Status: ACTIVE | VERIFIED | PROPOSED | DEPRECATED | DEAD (опционально)
  Files: пути к затронутым файлам
```

**Строгое правило:** Запись ADR должна начинаться с `` `ADR-XXX` `` в обратных кавычках, за которыми следует `[TYPE]` и `**Title**`. Заголовки markdown `###` для записей ADR ЗАПРЕЩЕНЫ (ломают парсер IPT).

**Пример:**
```
`ADR-O-358` [STANDARD] **Epistemic Player Integration** — Игрок как полноправный наблюдатель в EpistemicStore.
  Taboo: ❌ `if _nid == "player": continue`
  Status: ACTIVE
  Files: `svc/events/claim_event_subscriber.py`
```

**Type:** `STD` = Standard | `ONTO` = Ontology (ADR-O) | `FIX` = Verified Bugfix

**Формат файла аудита:** `docs/audits/ADR-0XX_IMPACT.md`
```markdown
# ADR-0XX Impact Audit
> Этот файл — детальный аудит ОДНОГО ADR. Единый атлас: `docs/ADR (Architecture Decision Records).md`

## Changed Domains
- [домены]

## Downstream Consumers
- [кто ещё читает эти данные]

## Runtime Impact
- [RAM/Latency]

## Sandbox Tests
- [ссылки на тесты]

## Rollback
- [как откатить]
```

**Нумерация:**
- Сначала прочитать `ADR` целиком — найти максимальный числовой ID.
- Новый ID = `max(существующие) + 1`.
- Для онтологических сдвигов: `ADR-O-XXX` (своя нумерация).
- Запрещено использовать ID сессии (`ADR-S##`) как ID ADR.

### 3. `DTO Registry` — АКТУАЛЬНЫЕ контракты

**Файл:** `docs/DTO Registry (Реестр контрактов).md`

**Когда обновлять:**
- Добавлен новый DTO.
- Изменены поля существующего DTO.
- Удалён DTO или поле.
- Изменён ownership (кто пишет/читает).

**Правила:**
- Прочитать файл целиком — найти секцию, к которой относится DTO.
- Вставить/обновить запись в формате: `**Name**` (`path/to/file.py`): описание + поля.
- Добавить `🚫 КАУЗАЛЬНЫЕ ЗАПРЕТЫ` если есть новые ограничения.

---

### 4. `ARCHITECTURE_FLOW` — топологическая карта (YAML-First)

**КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** редактировать `docs/ARCHITECTURE_FLOW_GENERATED.md` вручную.

**Единственный источник истины:** `architecture/*.yaml` (spatial, pipeline, physiology, authority, diagnostics, perception, identity, memory, economy, social, temporal, verbalization, frontend, manifestation, reaction, observed_fact_types, signal_causes, authoring/).

**Порядок обновления:**
1. Изменить `architecture/*.yaml` (добавить node, edge, constraint).
2. Выполнить: `python build_graph.py`.
3. Проверить `docs/ARCHITECTURE_FLOW_GENERATED.md` — Mermaid обновился.

**Файлы:**
- Источник: `architecture/*.yaml`
- Генератор: `build_graph.py`
- Результат (только чтение!): `docs/ARCHITECTURE_FLOW_GENERATED.md`

### 5. `LAST_SESSION.md` — снимок памяти для следующей сессии

**Файл:** `reports/LAST_SESSION.md`

Генерируется автоматически `CausalObserver` при завершении игры. **НЕ редактировать вручную** — только если CausalObserver не смог записать (краш).

**Что содержит:**
- DNA-метрики (SHI, NPI, OBI, SCF, CVS, PFI).
- Красные инварианты (с `suspect_files`).
- Состояние рендеринга (NPC с координатами, без координат).
- Movement Pipeline (по NPC: Intent, Score, Traversal, Координаты).
- Каузальные разрывы.
- Архитектурный долг.

## §4. Почему это важно

**`MUTATIONS.md`** говорит: «Создан CombatResolver как pure function».

**`ADR`** говорит ПОЧЕМУ: «LLM галлюцинирует при насилии, Python считает урон, мутация только через StateApplicator».

Если `ADR` нет — через месяц ИИ скажет: «Пусть CombatResolver сам меняет стейт, так быстрее». И сломает всё.

Если `DTO Registry` устарел — ИИ начнёт придумывать поля, которых нет.

Если `architecture/*.yaml` не обновлён — ИИ не увидит, что CombatResolver должен отдать дельту в StateApplicator, а сгенерированный Mermaid покажет дрейфующую, мёртвую архитектуру.

Если `LAST_SESSION.md` не прочитан — ИИ не узнает о красных инвариантах и начнёт строить новые фичи на сломанном фундаменте.

## §6. ТЕХЗАДАНИЕ ПРЕЕМНИКУ (обязательный вывод в конце сессии)

**Это НЕ файл.** Это текстовый блок, который LLM-архитектор ОБЯЗАНА вывести в конце сессии (в чате, прямо в браузере) — для передачи контекста следующей сессии.

### Правила вывода ТЗ

1. ТЗ выводится **после** всех изменений и §5 (финальная проверка).
2. ТЗ — это **единственный** текст, который следующая LLM-сессия прочитает первым (вместе с `reports/LAST_SESSION.md`).
3. ТЗ должно быть **самодостаточным** — следующая сессия понимает контекст без дополнительных вопросов.
4. ТЗ **не сохраняется в файл** — оно живёт только в выводе чата. Пользователь копирует его в начало следующей сессии.
5. ТЗ **обязательно** содержит Шаг 0 (Синхронизация реальности) с жёстким указанием «читать ЦЕЛИКОМ, без `-Last`».

### Шаблон ТЗ (заполнить и вывести в конце сессии)

```markdown
# ТЕХЗАДАНИЕ ПРЕЕМНИКУ (Снимок после S##)

**Дата:** [YYYY-MM-DD]
**Статус системы:** [IPT: N/N passed | pytest: N tests, M errors | CI: зелёный/красный]
**Последняя сессия:** S## — [краткое описание: что сделано]

---

## ШАГ 0: СИНХРОНИЗАЦИЯ РЕАЛЬНОСТИ (ОБЯЗАТЕЛЬНО ПЕРЕД СТАРТОМ)

В проекте параллельно работало несколько архитекторов. Опора на кэш прошлых сессий = архитектурный баг.

ПЕРЕД тем как предложить любое изменение кода, LLM ОБЯЗАНА прочитать файлы ЦЕЛИКОМ (без `Select-Object -Last`, без `-First`, без `-Index`):

1. Прочитать `docs/MUTATIONS.md` ЦЕЛИКОМ — `Get-Content docs/MUTATIONS.md` (узнать, что сделали другие, последняя сессия S##).
2. Прочитать `docs/ADR (Architecture Decision Records).md` ЦЕЛИКОМ — `Get-Content "docs/ADR (Architecture Decision Records).md"` (новые запреты и онтология).
3. Прочитать `docs/DTO Registry (Реестр контрактов).md` ЦЕЛИКОМ — актуальные поля DTO.
4. Прочитать `reports/LAST_SESSION.md` ЦЕЛИКОМ — красные инварианты, DNA-метрики.
5. Запросить АКТУАЛЬНЫЙ код через PowerShell (`Select-String`, `Get-Content`), прежде чем формировать патч БЫЛО/СТАЛО.

⚠️ ЗАПРЕЩЕНО: `Get-Content path | Select-Object -Last 60` — это чтение 8% файла, структура не видна, документы ломаются. Только `Get-Content path` без пайпов.

НИКАКИХ предположений о состоянии файлов на основе прошлых сессий. Только живая верификация через полное чтение.

### Контроль: что проверяет пользователь в ТЗ

Перед тем как принять ТЗ, пользователь проверяет:

1. **Шаг 0** содержит жёсткое «читать ЦЕЛИКОМ, без `-Last`».

4. **Известные баги** — таблица с ID, файлом, приоритетом.
5. **Опасные скрипты** перечислены.
6. **Запреты** — только актуальные для следующей сессии (не весь ADR, а то, что важно сейчас).
7. **Файлы для археологии** — конкретные пути, не «посмотри везде».
