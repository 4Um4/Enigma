**Основание:** ADR-O-435-R1–R5  
**Статус:** ARCHITECTURE DESIGN  
**Область:** Avatar Initiative + Intention Arbitration  
**Тип работы:** Read-only исследование и проектирование  
**Результат:** технический контракт, готовый к отдельному утверждению перед реализацией.

# 0. ЦЕЛЬ

Закрыть два фундаментальных архитектурных разрыва:

1. Самостоятельное формирование намерений Avatar.
2. Арбитраж независимых намерений Player и Avatar через одно физическое тело.

Фундаментальный принцип:

> Сознания независимы. Намерения независимы. Тело общее. Мир един.

R5.1 должен превратить этот принцип в конкретную систему причинных переходов.

Необходимо спроектировать не отдельную Avatar Initiative для речи, а универсальную архитектуру агентности.

Avatar должен иметь возможность:
- захотеть;
- сформировать собственное намерение;
- оценить возможность его исполнения;
- попытаться реализовать его через Body;
- столкнуться с противодействием Player;
- изменить или отозвать намерение;
- запомнить результат и изменить последующее поведение.

Player должен сохранять собственную агентность и возможность воздействовать на Body.

Ни один субъект не получает автоматического абсолютного права на тело.

# 2. ОБЛАСТЬ I — AVATAR INITIATIVE

## 2.1. Исходное состояние

Исследовать и связать в единую причинную модель:

- NPCState;
- drives_base;
- psyche;
- values;
- WillState;
- pressure_resistance;
- trauma_markers;
- identity_integrity;
- resentment;
- dependency;
- PerceptualKernel;
- AffectiveIntegrator;
- BeliefCrystallizationEngine;
- EpistemicStore;
- EventMemory;
- CharacterProfile.

Установить, какие данные действительно существуют, как обновляются и какие компоненты имеют право их изменять.

Не считать наличие полей доказательством существования полноценного когнитивного процесса.

## 2.2. Спроектировать универсальный механизм возникновения намерений

Требуется построить причинную модель:

```text
SUBJECTIVE STATE
    ↓
PERCEPTION
    ↓
INTERPRETATION
    ↓
BELIEFS / MEMORY / VALUES / DRIVES
    ↓
DESIRE FORMATION
    ↓
INTENTION FORMATION
    ↓
INTENTION PROPOSAL
```

Необходимо определить семантическую границу между:

1. Внутренним состоянием субъекта.
2. Возникновением желания.
3. Формированием намерения.
4. Выбором между конкурирующими намерениями самого субъекта.
5. Предложением намерения на исполнение.
6. Фактическим допуском к Body.

Это разные процессы. Не объединять их в одну функцию без обоснования.

## 2.3. Выбор архитектурной модели

Рассмотреть минимум три подхода:

- BDI-подобная модель (beliefs, desires, intentions).
- Модель формирования намерений на основе внутренних потребностей и субъективной оценки состояния.
- Гибридная модель, использующая существующие когнитивные механизмы ENIGMA.

Для каждого подхода определить:
- соответствие существующему коду;
- выразительность поведения;
- возможность автономной инициативы;
- поддержку разных личностей;
- устойчивость к повторению однотипных реакций;
- детерминированность;
- стоимость вычислений;
- сложность сохранения состояния;
- возможность последующего расширения.

Выбрать один рекомендуемый вариант.

Не копировать DecisionHub механически. Но и не отвергать существующие механизмы только потому, что они создавались для NPC.

Если часть DecisionHub пригодна для повторного использования, доказать это.

## 2.4. Запрет на сценарное поведение

Не проектировать систему в виде набора фиксированных реакций:

```python
if fear > 0.8:
    retreat()
```

Не использовать произвольные пороги, ручные таблицы реакций и сценарные исключения как фундамент агентности.

Нужно показать, как разные значения личности, убеждений, опыта и текущего восприятия способны приводить к различным намерениям через один универсальный механизм.

Не требовать случайности ради разнообразия.

## 2.5. Универсальность классов действий

Механизм должен быть независим от конкретного типа действия.

Проверить возможность формирования намерений:

- речевых;
- двигательных;
- защитных;
- социальных;
- исследовательских;
- конфликтных;
- направленных на сопротивление Player;
- направленных на восстановление контроля над телом.

Это не перечень обязательных немедленных реализаций, а проверка универсальности контракта.

**Нельзя проектировать Avatar Initiative как CommunicationIntent с дополнительными полями.** Речь — лишь один из возможных результатов агентности.

## 2.6. Результат области

Представить:

1. Причинную диаграмму Avatar Initiative.
2. Контракт формирования желания.
3. Контракт формирования намерения.
4. Контракт предложения намерения.
5. Состояния намерения и переходы между ними.
6. Механизм отзыва, изменения и замены намерения.
7. Связь с памятью и убеждениями.
8. Список переиспользуемых механизмов.
9. Недостающие ответственности.
10. Рекомендуемую архитектуру.

# 3. ОБЛАСТЬ II — INTENTION MODEL

До проектирования арбитража необходимо определить, что именно конкурирует за тело.

## 3.1. Единая семантика намерения

Исследовать существующие:

- InterventionEvent;
- CommunicationIntent;
- ActionIntent;
- AgentAction;
- ActionConsequenceCompiler;
- action execution contracts;
- существующие очереди и механизмы обязательств.

Определить, можно ли привести их к общему понятию намерения без разрушения текущей семантики.

Разделить:

| Понятие | Значение |
|---|---|
| Desire | Субъект хочет определённого состояния |
| Intention | Субъект решил стремиться к определённому результату |
| Proposal | Намерение предложено для исполнения |
| Commitment | Субъект сохраняет намерение во времени |
| Authorization | Намерение допущено к исполнению |
| Execution | Физическое действие выполняется |
| Outcome | Фактическое последствие действия |

Не считать эти состояния взаимозаменяемыми.

## 3.2. Владелец намерения

Каждое намерение должно сохранять информацию:

- кто его сформировал;
- к какому субъекту относится;
- через какое тело предполагается исполнение;
- какого результата субъект добивается;
- какие ограничения исполнения существуют;
- какое намерение оно заменяет или продолжает;
- в каком состоянии находится.

Определить, какие сведения необходимы в самом контракте, а какие должны оставаться внешней provenance-информацией.

Не создавать поля только ради полноты таблицы.

## 3.3. Жизненный цикл

Предложить формальную машину состояний:

```text
FORMED
    ↓
PROPOSED
    ↓
CONFLICT_CHECK
    ↓
AUTHORIZED / REJECTED / DEFERRED
    ↓
EXECUTING
    ↓
COMPLETED / FAILED / INTERRUPTED
```

Это исходная схема для анализа, не обязательная окончательная модель.

Определить:
- отмену;
- замену;
- повторное предложение;
- несовместимость;
- устаревание;
- прерывание;
- невозможность физического исполнения.

Особенно важно: неисполненное намерение не должно бесследно исчезать, если оно продолжает иметь значение для субъекта.

# 4. ОБЛАСТЬ III — BODY ACTION ARBITRATION

## 4.1. Археология существующего исполнения

Проследить полный путь:

```text
Player Input
    → InterventionEvent
    → Phase 1
    → WillpowerGate
    → Action Execution
    → EventDTO
    → WORLD TRUTH
```

Отдельно исследовать все остальные пути, способные изменять Body:

- NPC и автономные действия;
- боевые действия;
- movement;
- защитные реакции;
- асинхронные результаты;
- системные эффекты;
- последствия событий;
- внешние контроллеры;
- прямые изменения NPCState.

Составить карту всех точек физического воздействия на Body.

## 4.2. Проверка атомарности

Проверить утверждение:

> Один Body может исполнить только одно несовместимое физическое действие в пределах одного tick.

Не выводить это из единственной точки входа TickOrchestrator.

Доказать:

- где начинается физическое исполнение;
- где оно считается принятым;
- где оно становится необратимым;
- какие компоненты могут его обойти;
- сколько независимых исполнителей могут изменить Body;
- возможны ли два конфликтующих воздействия в разных фазах;
- как обрабатываются составные действия.

Разделить:
- одно намерение;
- одно исполнение;
- одну физическую операцию;
- несколько последствий;
- несколько событий мира.

## 4.3. Общий арбитраж

Спроектировать единый механизм допуска намерений:

```text
PLAYER INTENTION ──────┐
                       │
AVATAR INTENTION ──────┼──→ BODY ACTION ARBITRATION
                       │              ↓
AUTHORIZED SYSTEM ─────┘        EXECUTION DECISION
                                      ↓
                                  BODY
                                      ↓
                                  WORLD TRUTH
```

Общий арбитраж не должен формировать желания или намерения.

Он получает уже сформированные намерения и решает вопрос их физической совместимости и допуска.

## 4.4. Конфликтные ситуации

Спроектировать обработку:

**A. Совместимые намерения**

Player хочет говорить, Avatar хочет продолжить движение, если оба действия физически совместимы.

Определить, возможно ли совместное исполнение или требуется последовательность.

**B. Противоположные намерения**

Player хочет атаковать, Avatar хочет отступить.

**C. Avatar сопротивляется Player**

Player хочет атаковать, Avatar не соглашается.

**D. Player противодействует Avatar**

Avatar хочет отступить, Player выдаёт команду двигаться вперёд.

**E. Два намерения одного субъекта**

Avatar хочет одновременно приблизиться к NPC и избежать контакта с ним.

**F. Невозможность исполнения**

Body мёртв, обездвижен, ранен или физически не способен выполнить действие.

**G. Прерывание**

Во время исполнения возникает внешнее событие, меняющее допустимость действия.

Для каждого случая описать:
- состояние обоих намерений;
- решение арбитража;
- результат для Body;
- последствия для каждого субъекта;
- запись в памяти;
- события WORLD TRUTH.

## 4.5. WillpowerGate

Сохранить существующую ответственность WillpowerGate:

**сопротивление Avatar воздействию Player.**

Не превращать его в универсальный арбитр.

Определить его точное место относительно:
- формирования намерения;
- конфликта намерений;
- авторизации;
- исполнения.

Если существующая семантика требует коррекции, обосновать её.

## 4.6. Приоритеты

Не вводить бездоказательные правила:

- Player всегда первый;
- Avatar всегда первый;
- последнее намерение побеждает;
- более сильное желание всегда побеждает;
- движение важнее речи;
- сопротивление всегда блокирует действие.

Нужно предложить механизм, учитывающий природу конфликта, внутреннее состояние субъектов, физическую допустимость и уже существующие обязательства.

Не путать детерминированность с жёсткой таблицей приоритетов.

Если два состояния идентичны, результат должен быть воспроизводимым. Но воспроизводимость сама по себе не объясняет правильность решения.

## 4.7. Результат области

Представить:

1. Контракт общего арбитража.
2. Правила совместимости действий.
3. Правила разрешения конфликтов.
4. Границу физического исполнения.
5. Гарантии атомарности.
6. Судьбу отклонённых и отложенных намерений.
7. Защиту от двойного исполнения.
8. Сохранение причинной детерминированности.

# 5. ОБЛАСТЬ IV — INV-PLAYER-AUTHORSHIP

Исследовать инвариант целиком.

Обеспечить:

- Player остаётся автором своих вмешательств.
- Avatar остаётся автором собственных намерений.
- NPC не может выдавать себя за Avatar.
- Avatar не классифицируется как NPC.
- Avatar не классифицируется как PLAYER_INPUT.
- Не возникает неявного разрешения через fallback в NPC_DECISION.
- Физический исполнитель не становится автоматически автором намерения.

Предложить явную модель полномочий и границ авторизации.

Показать, как общий арбитраж сохраняет INV-PLAYER-AUTHORSHIP, а не обходит его.

# 6. ОБЛАСТЬ V — BODY УТРАЧЕНО ИЛИ НЕДОСТУПНО

R5 показал, что при смерти Body идентичности Player и Avatar сохраняются, но физические действия становятся невозможны.

Необходимо определить поведение намерений:

- Может ли Avatar продолжать воспринимать и формировать намерения?
- Какие процессы продолжаются без Body?
- Какие намерения могут оставаться активными?
- Какие намерения теряют физическую возможность исполнения?
- Что происходит с Player input?
- Может ли существовать новый Body?
- Как сохраняется связь субъекта с телом при возможной смене носителя?

Не проектировать новую механику переселения или воскрешения без подтверждения авторского замысла.

Но архитектура не должна ошибочно связывать существование сознания с наличием одного конкретного NPCState.

# 7. ИНТЕГРАЦИОННЫЕ СЦЕНАРИИ

Обязательно разобрать восемь случаев.

1. Player бездействует — Avatar самостоятельно формирует и исполняет намерение.
2. Player командует — Avatar принимает команду.
3. Player и Avatar хотят противоположного.
4. Avatar хочет действовать — Player активно противодействует.
5. Оба субъекта формируют совместимые намерения.
6. Avatar хочет физически действовать, но Body недоступно.
7. Во время исполнения возникает внешнее прерывание.
8. Одно намерение создаёт несколько событий-последствий.

Каждый сценарий показать через реальные состояния и причинные переходы, а не только текстовое описание.

# 8. ВЗАИМОДЕЙСТВИЕ С ОСТАЛЬНОЙ АРХИТЕКТУРОЙ

R5.1 не должен заново проектировать Identity, Communication, Ceremony и Memory.

Но необходимо установить точные интерфейсы с ними:

- Identity — кто является владельцем намерения.
- Communication — как речевое намерение превращается в физическое высказывание.
- Ceremony — когда намерения могут формироваться и исполняться.
- Memory — как субъекты узнают об успехе, отказе и последствиях.
- EpistemicStore — как результаты изменяют убеждения.
- WORLD TRUTH — как физическое исполнение становится единым событием мира.

Если обнаружится блокирующее противоречие в этих областях, зафиксировать его отдельно. Не расширять R5.1 без необходимости.

# 11. КРИТЕРИИ ЗАКРЫТИЯ

R5.1 считается завершённым, если:

- [ ] Avatar способен формировать намерения без Player command.
- [ ] Формирование намерений не ограничено речью.
- [ ] Механизм поддерживает разные личности Avatar без программирования реакций под каждую.
- [ ] Желание, намерение, предложение и исполнение семантически разделены.
- [ ] Player и Avatar имеют независимые источники намерений.
- [ ] Существует общий арбитраж физического исполнения.
- [ ] Совместимые намерения могут быть обработаны корректно.
- [ ] Несовместимые намерения не приводят к двойному исполнению.
- [ ] WillpowerGate сохраняет свою отдельную ответственность.
