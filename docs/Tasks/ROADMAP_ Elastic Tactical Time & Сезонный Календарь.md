## 6. ROADMAP: Elastic Tactical Time & Сезонный Календарь

Это задача будущих спринтов. Реализация требует глубокой интеграции с Dual-Time Ontology (ADR-058, ADR-059). 

### 6.1. Elastic Tactical Time (Slow-mo при вводе)

**Цель:** Мир живёт постоянно (тики идут всегда), но когда игрок начинает вводить текст, скорость симуляции снижается (slow-mo), давая время на реакцию.

**Ключевой принцип (ADR-058/059):** Каузальный тик (`scene_state["tick"]`, +1 за шаг) **не замедляется**. Причинность неделима. Замедляется только **Календарь** (`game_time_seconds`).

**Где искать и что менять:**

1. **Фронтенд (`frontend/game_screen.py`, `frontend/text_input.py`):**
   - Сейчас `idle_tick` вызывается по таймеру `IDLE_TICK_NEAR_MS`. 
   - **Что сделать:** Фронтенд должен посылать `idle_tick` запросы с *постоянным реальным интервалом* (например, каждые 2 сек), чтобы бэкенд не "засыпал".
   - При фокусе на `TextInput` (игрок начал печатать), фронтенд добавляет в запрос параметр `time_scale: float` (например, `0.2` для slow-mo).
   - Когда фокус теряется (отправка сообщения), `time_scale` возвращается к `1.0` (или `5.0` для ускорения ожидания).

2. **API Слой (`backend/app/api/routes.py`):**
   - Эндпоинт `/api/game/idle_tick` должен принимать опциональный параметр `time_scale: float = 1.0` и прокидывать его в `GameLoop`.

3. **GameLoop (`backend/app/services/game_loop/__init__.py`):**
   - Метод `idle_tick` принимает `time_scale`.
   - Передаёт его в `TickOrchestrator`.

4. **TickOrchestrator (`backend/app/services/tick_orchestrator.py`):**
   - Метод `_advance_idle_time` (строка ~1159). Сейчас он делает: `new_seconds = Calendar.advance(current_seconds, GAME_TICK_INTERVAL_SECONDS)`.
   - **Что сделать:** Заменить на `Calendar.advance(current_seconds, int(GAME_TICK_INTERVAL_SECONDS * time_scale))`.
   - **Результат:** Каузальный тик инкрементируется как обычно (+1), NPC думают, физика работает. Но календарное время продвигается медленнее (или быстрее). Lerp на фронтенде (основанный на `duration_ticks`) останется плавным.

### 6.2. Сезонный Календарь (Года, Времена года)

**Цель:** Введение цикличных сезонов (Весна, Лето, Осень, Зима) и смены лет, влияющих на геймплей (погода, доступность локаций, поведение NPC).

**Где искать и что менять:**

1. **Домен Времени (`backend/app/core/calendar.py`):**
   - Сейчас класс `Calendar` примитивен (форматирование HH:MM).
   - **Что сделать:** Ввести онтологию `WorldDate(year, season, day, hour)`. Создать маппинг `game_time_seconds → WorldDate`.
   - Определить константы: `SEASON_DURATION_SECONDS`, `YEAR_DURATION_SECONDS`.
   - Добавить метод `Calendar.get_season(game_time_seconds) -> Season`.

2. **Окружение (`backend/app/services/scene_state_manager.py`):**
   - В `_default_scene_state` и сборке снапшота добавить поля `season`, `year`, `day_of_year` в секцию `environment`.
   - Погода (`weather`) должна генерироваться на основе `season`, а не быть статичной.

3. **Влияние на NPC (`backend/app/services/npc/life_engine.py`):**
   - Расписания NPC (`schedules`) должны поддерживать сезонные сдвиги (например, фермер работает летом, зимой сидит в таверне). 
   - Это потребует расширения формата `archetypes/*.json` для поддержки сезонных вариантов расписаний.

4. **Фронтенд (`frontend/game_screen.py`):**
   - Отрисовка календаря в HUD (уже есть `format_world_date`, нужно расширить для вывода "Лето, День 15").

**Предупреждение для архитектора:** Не привязывайте каузальные механики (длительность движения, кулдауны способностей) к `game_time_seconds`. Они должны зависеть только от `tick` (ADR-059). Календарь — это декорация и макро-модификатор, а не двигатель симуляции.
