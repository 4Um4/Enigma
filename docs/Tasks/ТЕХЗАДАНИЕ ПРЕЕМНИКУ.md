## 1. Текущее состояние системы

```
все тики → TickOrchestrator.execute()
              ├─ idle (dm_ctx=None):   0→0.5→1→2→3→4→5→6→8→9→10
              └─ player (dm_ctx=...):  _phase_5_player_decision → _phase_6_post_decision
                                        → execute_player_finalize → 0.5→8→9→10
```

**Что работает:**
- **StateDeltas v2 (Domain-Tagged Typed Payloads) — ЯДРО МИГРИРОВАНО.**
- Фаза 0.5 и Фаза 8 генерируют типизированные frozen payload (`SocialPayload`, `EmotionPayload`, `ReputationPayload`, `IdentityPayload`).
- `_aggregate_deltas()` группирует по `(npc_id, domain, target)` и мержит frozen payload'ы.
- `StateApplicator._apply_deltas()` читает данные из payload с fallback на v1 поля.
- `ReactionSubscriber` разделён на 2 доменные дельты (`EMOTION` + `SOCIAL`) вместо 1 смешанной.
- `propagate_social_rumors` разделён на 2 доменные дельты (`EMOTION` + `SOCIAL`).
- 400 тестов проходят + 10 новых тестов v2 контракта.
- **DecisionHub оставлен на v1** (`domain=None`, `payload=None`). `StateApplicator` обрабатывает его через v1 fallback.
- Фаза 0.5 (time-driven decay) — SocialDecayHandler + ReputationDecayHandler — ВЫПОЛНЯЕТСЯ ВСЕГДА
- Фаза 8 (event-driven) — PerceptionSubscriber → ReactionSubscriber → SocialSubscriber — фиксированный порядок
- Фаза 8 delta_buffer flush — после цикла обработчиков, ДО Фазы 9
- StateDeltas маршрутизация: intent_target / social_target / faction_id с __post_init__
- StateApplicator.apply_batch() — единый мутатор, тонкий мост dict↔NPCState
- Closing drift — `if |base-current| < EPSILON: drift = base - current`
- _build_npc_snapshots() — маппинг social_stats → relationship_cache вложенного формата
- NPC-to-NPC Social Relations Enrichment — _enrich_with_social_relations() обогащает NPC dict из village_relations.json (шкала 0-1→0-100)

**Ключевой контракт v2:**
```python
# StateDeltas v2: domain определяет тип payload
# __post_init__: payload тип должен соответствовать domain, иначе TypeError
# StateApplicator маршрутизация:
#   domain == REPUTATION → ReputationEngine
#   domain == SOCIAL → RelationshipStore (trust/fear)
#   domain == EMOTION → NPCState.psyche (stress/emotion)
#   domain is None → v1 fallback (intent_target/social_target/faction_id)

# _aggregate_deltas v2:
#   Ключ: (npc_id, domain, target). Фолбэк для v1: None + v1 таргеты.
#   Merge: суммирование v1 полей + _merge_payloads для frozen dataclasses
```

**Задачи:**

3. НЕ создавать параллельный snapshot в domain/ — расширить существующий
4. Тесты: новые поля корректно маппятся

## 4. Архитектурные ограничения (нарушение = баг)

1. **Typed Payloads, не Dict[str, Any].** Каждый DeltaDomain имеет свой frozen dataclass payload. `payload: Dict[str, Any]` запрещён. Новый domain = новый payload class + регистрация в `_DOMAIN_PAYLOAD_MAP`.
2. **Единый мутатор.** `StateApplicator.apply_batch()` — единственная точка применения дельт. CombatResolver возвращает StateDeltas (domain=COMBAT), они идут через delta_buffer → apply_batch.
3. **CombatResolver = Pure Function.** Никакого state, никаких side effects, никакого event_bus.publish() внутри. Только `(snapshot, intent) → deltas`.
4. **Фаза 0.5 = time-driven, Фаза 8 = event-driven.** Combat — event-driven → Фаза 8 (CombatSubscriber).
5. **Единый NPCStateSnapshot.** Не создавать параллельный snapshot в domain/. Расширять существующий в idle_tick.py.
6. **Все дельты через delta_buffer.** Combat дельты — не исключение. Не мутировать all_npcs_raw напрямую.
7. **Closing drift, не forced drift.** `if |base-current| < EPSILON: drift = base - current`.
8. **Репутация ≠ trust.** `reputation_delta` только с faction_id (domain=REPUTATION). `trust_delta` только с social_target/intent_target (domain=SOCIAL).
9. **Phase 8 порядок: perception → reaction → social → combat.** Combat обрабатывает после социальных реакций.
10. **perceiving_npcs семантика: None vs [].** `None` = fallback на всех. `[]` = никто не увидел.
11. **StateDeltas v1 поля DEPRECATED.** Запрещено добавлять новые поля в v1. Путь: v2 payload. Удаление v1 полей — после миграции DecisionHub.

## 8. Контекст решений

**Почему StateDeltas v2 реализован через Typed Payloads, а не Dict[str, Any]:**
Мастер Тай абсолютно прав: переход от «типов состояний» к «протоколу изменений мира» — это суть. Но протокол должен быть **типизированным протоколом**, не словарём. Frozen dataclass стоит 5 строк кода, но даёт IDE autocomplete, защиту от опечаток (TypeError) и лёгкий рефакторинг. `Dict[str, Any]` — это «Unity syndrome», потеря discoverability через string keys.

**Почему ReactionSubscriber и propagation разделены на 2 дельты (EMOTION + SOCIAL):**
В v1 одна реакция порождала микс (stress + trust) в одной дельте. Это нарушает принцип Domain-Tagged разделения. В v2 одна реакция порождает 2 дельты, каждая в своём домене. Это идеально ложится в `aggregate_deltas()`, который суммирует дельты по `(npc_id, domain, target)`.

**Почему DecisionHub пока на v1:**
DecisionHub возвращает `DecisionResult.deltas: StateDeltas`. Чтобы мигрировать его на v2, нужно изменить контракт на `List[StateDeltas]`, так как решение может порождать EMOTION + SOCIAL дельты. Это каскадное изменение по всему пайплайну. Пока `StateApplicator` имеет безопасный v1 fallback, это не блокирует боёвку.

**Почему NPCStateSnapshot расширяем, а не создаём новый:**
Два snapshot'а = два источника истины. _build_npc_snapshots() уже делает маппинг. Добавить hp/pain/abilities — 5 строк кода. Создать параллельный — 50 строк + синхронизация.

**Почему WillpowerGate — только дизайн:**
Avatar — это новый NPC. Он проходит через все 10 фаз. Его DecisionHub, TopicExtractor, MemoryProcessor — всё это нужно. Но боевка даёт больше геймплея быстрее. WillpowerGate без боёвки = Аватар отказывается атаковать, но атаки всё равно нет.
