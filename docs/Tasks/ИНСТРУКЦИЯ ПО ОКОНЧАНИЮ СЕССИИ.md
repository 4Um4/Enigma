Вот список того, что ты должен обновлять/генерировать по завершении этапа:

### 1. ADR (Architecture Decision Records) — Записи об архитектурных решениях
Это самое важное, что назвал Тай. `MUTATIONS.md` говорит: *"Создан CombatResolver как pure function"*. ADR говорит **ПОЧЕМУ**.

Если этого нет, через месяц ИИ (или ты сам) скажет: "Зачем мне чистая функция? Пусть CombatResolver сам меняет стейт NPC, так быстрее". И сломает всё.

**Формат ADR (создается в `/docs/adr/`):**
*   **Title:** Использование Pure Functions для расчета боя
*   **Context:** LLM галлюцинирует при физическом насилии, нужно чтобы Python жестко считал урон, но нельзя допустить деградации стейта внутри боя.
*   **Decision:** CombatResolver принимает замороженный `NPCStateSnapshot` и возвращает только `DamageDelta`. Мутацию делает только `StateApplicator`.
*   **Consequences:** Безопасность (бой не сломает ядро), но нужно писать мапперы снапшотов, что увеличивает объем кода.

### 2. DTO Registry (Реестр контрактов / Словарь данных)
Твой проект живет на DTO. Если ИИ забудет, какие поля есть в `DamageDelta`, он начнет их придумывать (галлюцинировать). 

После каждого спринта ты должен выгружать актуальную структуру всех DTO в один файл. Это "словарь" для ИИ.

**Формат (например, `/docs/DTO_REGISTRY.md`):**
```markdown
## DamageDelta
- target_id: str
- body_zone: BodyZone (enum: HEAD, TORSO, etc.)
- blunt_force: float (0.0-1.0)
- pain: float (0.0-1.0)
- bleeding_rate: float

## WorldEnvironmentDTO
- time_of_day: float (0.0-23.99)
- weather_type: str
- temperature: float
```
*Зачем:* Когда ты даешь ИИ задачу на новый код, ты кидаешь ему Устав, CSV-граф и этот Реестр. ИИ мгновенно понимает, какими типами данных он имеет право оперировать.

### 3. Обновленный CSV-граф (Топологическая карта)
Ты уже используешь CSV для передачи контекста. Но после внедрения новых систем (Боевка, Среда, Погода) граф связей меняется. 

После спринта ты должен обновить CSV, добавив новые узлы и потоки данных.

**Было:**
```csv
Entity,Type,Receives From,Sends To,DTO
DecisionHub,Service,EventBus,LLM_Prompt,CommunicationIntent
```

**Стало (после Шага 2 и Среды):**
```csv
Entity,Type,Receives From,Sends To,DTO
DecisionHub,Service,EventBus,CombatResolver,CombatRequest
CombatResolver,Service,DecisionHub,StateApplicator,DamageDelta
StateApplicator,Service,CombatResolver,SqlitePersist,InjuryDTO
Avatar,NPC,SurfaceLogic,EventBus,LoudNoiseEvent
```
*Зачем:* Это единственный способ для ИИ увидеть всю систему целиком, не читая тысячи строк кода. Если ИИ не увидит, что `CombatResolver` должен отдать дельту в `StateApplicator`, он попытается написать в БД напрямую.

### Итоговый чеклист окончания спринта

Когда ты завершаешь крупную фичу (например, Шаг 2: Combat Skeleton), ты делаешь 4 вещи:

1.  **Очищаешь контекст ИИ** (начинаешь новую сессию).
2.  **Пишешь 1-2 записи в `MUTATIONS.md`** (Что добавлено/изменено).
3.  **Пишешь 1 ADR** (Почему принято именно такое архитектурное решение).
4.  **Обновляешь `DTO_REGISTRY.md`** (Добавляешь новые DTO).
5.  **Обновляешь `ARCHITECTURE_FLOW.md`** — Вот сюда ты кладешь код Mermaid.

Когда ты заканчиваешь спринт, ты обновляешь архитектурный снимок. В папке /docs/ у тебя теперь лежит:

Этот набор файлов (Устав + CSV + Реестр + Мутации + ADR) — это **снимок памяти твоего проекта**. С ним любая новая LLM-сессия подхватит контекст за 30 секунд и не сломает архитектуру.
