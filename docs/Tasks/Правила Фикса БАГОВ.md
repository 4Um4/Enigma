# ENIGMA — ПРОТОКОЛ РАЗБОРА PIPELINE-БАГОВ И ДЕГРАДАЦИИ СИМУЛЯЦИИ

## ЦЕЛЬ

При обнаружении:

* повторяющихся ошибок,
* деградации поведения NPC,
* потери движения,
* рассинхронизации state,
* nondeterministic поведения,
* tuple/list/object mismatch,
* silent corruption,
* частичного применения изменений,

LLM НЕ ДОЛЖНА:

* предлагать случайные фиксы,
* менять архитектуру вслепую,
* «пробовать варианты»,
* вносить speculative refactor.

LLM обязана:

1. локализовать стадию отказа,
2. восстановить pipeline причинности,
3. определить ownership данных,
4. проверить архитектурный контракт между слоями,
5. минимально вмешаться,
6. сохранить совместимость со всеми downstream слоями.

---

# ЧАСТЬ I — ГЛАВНОЕ ПРАВИЛО

## НИКОГДА НЕ ФИКСИТЬ СИМПТОМ ДО ВОССТАНОВЛЕНИЯ PIPELINE

Ошибка:

```python
too many values to unpack
```

НЕ означает:

> «нужно поправить unpack»

Она означает:

> «два слоя не согласны о структуре данных».

---

# ЧАСТЬ II — ОБЯЗАТЕЛЬНАЯ ПРОЦЕДУРА

# ШАГ 1 — ОПРЕДЕЛИТЬ PIPELINE OBJECT

Сначала определить:

Что именно движется через pipeline?

Например:

* EventContext
* MovementIntent
* SceneChange
* TickResult
* NPCState
* DecisionFrame

---

# ШАГ 2 — ВОССТАНОВИТЬ TOPOLOGY

LLM обязана восстановить:

```text
КТО СОЗДАЁТ
→ КТО ЧИТАЕТ
→ КТО ТРАНСФОРМИРУЕТ
→ КТО ПОГЛОЩАЕТ
→ КТО КОММИТИТ
```

Пример:

```text
update_routine()
→ _simulate_major()
→ process_intents()
→ SceneChange
→ SceneStateManager.apply_changes()
→ npc.position
```

Пока topology не восстановлена —
фикс запрещён.

---

# ШАГ 3 — ОПРЕДЕЛИТЬ OWNER СТАДИИ

Для каждого объекта определить:

| Объект         | Кто владелец      |
| -------------- | ----------------- |
| MovementIntent | MovementEngine    |
| SceneChange    | SceneStateManager |
| NPCState       | RuntimeStore      |
| DecisionScore  | DecisionHub       |

---

# ШАГ 4 — ПРОВЕРИТЬ CONTRACT

LLM обязана проверить:

## 1. Что функция принимает

Пример:

```python
def process_intents(
    intents: list[MovementIntent]
)
```

## 2. Что функция возвращает

Пример:

```python
-> list[SceneChange]
```

## 3. Что ожидает caller

Пример:

```python
changes, intent = ...
```

## 4. Совпадают ли контракты

Если нет —
это boundary violation.

---

# ШАГ 5 — ОПРЕДЕЛИТЬ STAGE OF FAILURE

LLM обязана определить:

| Стадия    | Проверка                    |
| --------- | --------------------------- |
| CREATE    | объект создан?              |
| PASS      | объект передан дальше?      |
| TRANSFORM | объект изменён корректно?   |
| APPLY     | изменения применены?        |
| COMMIT    | state сохранён?             |
| RELOAD    | state не перезаписан позже? |

---

# ЧАСТЬ III — ЗАПРЕЩЁННЫЕ ДЕЙСТВИЯ

LLM НЕ ДОЛЖНА:

## 1. Менять return type без анализа downstream

Запрещено:

```python
return changes, intents
```

если downstream ожидает:

```python
return changes
```

---

## 2. Добавлять временные tuple/list-хаки

Запрещено:

```python
if isinstance(result, tuple):
```

без понимания ownership.

---

## 3. Вносить speculative refactor

Запрещено:

* переносить MovementEngine,
* менять orchestrator,
* двигать apply_changes,
* менять event ownership,

если root cause не локализован.

---

## 4. Игнорировать partial corruption

Особо опасно:

```python
часть изменений применена
часть нет
тик продолжился
```

Это:

# silent simulation corruption

# ЧАСТЬ IV — ОБЯЗАТЕЛЬНЫЕ ИНСТРУМЕНТЫ DEBUG

# 1. PIPELINE TRACE

LLM должна рекомендовать trace chain:

```text
Intent Created
Intent Processed
SceneChange Emitted
SceneChange Applied
NPC State Saved
```

---

# 2. CONTRACT ASSERTIONS

DEV-режим обязан содержать:

```python
assert isinstance(change, SceneChange)
```

---

# 3. STRUCTURED LOGGING

Запрещены логи вида:

```text
[LIFE_ENGINE] error
```

Нужны:

```text
[PIPELINE][INTENT_CREATE]
[PIPELINE][INTENT_CONSUME]
[PIPELINE][SCENE_APPLY]
[PIPELINE][STATE_COMMIT]
```

---

# 4. SNAPSHOT REPLAY

Каждый tick должен быть replayable.

Минимум:

* tick_id
* scene_state
* npc_state
* emitted_events
* scene_changes

# ЧАСТЬ VI — ГЛАВНЫЕ СИМПТОМЫ АРХИТЕКТУРНОЙ ДЕГРАДАЦИИ

Если наблюдается:

| Симптом                     | Значение                   |
| --------------------------- | -------------------------- |
| tuple/list mismatch         | потеря contract discipline |
| object has no attribute     | boundary corruption        |
| repeated fallback behavior  | silent upstream failure    |
| NPC не двигаются, но думают | pipeline split             |
| state reset между тиками    | ownership conflict         |
| часть системы работает      | partial commit             |
| nondeterministic bug        | mutable shared state       |

---

# ЧАСТЬ VII — ПРАВИЛО ENIGMA

## НИКАКИХ RAW STRUCTURES МЕЖДУ СЛОЯМИ

Запрещено:

```python
list
tuple
dict
```

между major pipeline stages.

Разрешено только:

```python
TickResult
MovementResult
SceneApplyResult
DecisionFrame
PerceptionResult
```

---

# ЧАСТЬ VIII — ОСНОВНАЯ МЫСЛЬ

Сложная симуляция умирает не от:

* плохого AI,
* слабого LLM,
* медленного кода.

Она умирает от:

# потери наблюдаемости pipeline.

Когда:

* уже нельзя понять,
* где объект родился,
* кто его изменил,
* кто обязан его уничтожить,
* и кто последний видел его валидным.

---

# ЧАСТЬ IX — ОСОБО ВАЖНО ДЛЯ LLM

LLM обязана помнить:

## В Enigma:

* pipeline важнее feature,
* determinism важнее скорости,
* contracts важнее convenience,
* ownership важнее «гибкости»,
* observability важнее clever-кода.

---

# ЧАСТЬ X — ПРАВИЛО ФИНАЛЬНОГО ФИКСА

После нахождения root cause LLM обязана:

1. Объяснить:

   * почему возник баг,
   * какой слой нарушил контракт,
   * кто владелец данных.

2. Предложить:

   * минимальный фикс,
   * без архитектурного drift.

3. Проверить:

   * downstream compatibility,
   * replay stability,
   * deterministic behavior.

4. Указать:

   * какие future bugs предотвращены,
   * какие architectural risks остались.
