# 1. Цель Stage 2

Построить минимально полноценный **телесный контур автономной жизни NPC**, который существует независимо от игрока и является причинной основой дальнейшей психики.

После Stage 2 NPC должен не просто:

> «иметь параметры голода, усталости и здоровья»,

а должен:

> **физиологически жить во времени, испытывать изменяющиеся внутренние состояния, самостоятельно искать способы удовлетворения базовых потребностей, получать физические последствия своих решений и восстанавливаться/ухудшаться в зависимости от истории.**

Главный результат:

```text
TIME
 ↓
BODY
 ↓
PHYSIOLOGICAL STATE
 ↓
NEEDS / URGENCY
 ↓
BEHAVIOR PRESSURE
 ↓
ACTION
 ↓
WORLD CONSEQUENCE
 ↓
BODY
```

Это должен стать **первый замкнутый жизненный контур ENIGMA**.

# 2. Критический архитектурный долг, который Stage 2 обязан закрыть

До расширения физиологии необходимо устранить два наблюдаемых класса поведения.

## ПРОБЛЕМА A — Intent/Action Divergence

NPC сообщает/фиксирует намерение:

```text
«есть»
«спать»
«идти домой»
«остановиться»
```

но фактически продолжает:

```text
ходить по старому маршруту
объединяться в группу
разговаривать
повторять предыдущий action
```

То есть:

```text
INTENT ≠ EXECUTED ACTION
```

Это не cosmetic bug.

Это нарушение основного causal contract ENIGMA.

Если NPC хочет сделать A, но мир продолжает делать B, то любые будущие:

* голод;
* эмоции;
* отношения;
* экономика;
* профессии;
* убеждения;
* планы

будут строиться поверх ложной истории.

---

# 3. Новое обязательное правило: Intent не является исполненным действием

Архитектурно необходимо различать:

```text
Intent
```

и:

```text
Action
```

и:

```text
Execution
```

и:

```text
Observed Result
```

Минимальный цикл:

```text
Intent
 ↓
Commitment
 ↓
Action Plan / Action Task
 ↓
Executor
 ↓
Execution Result
 ↓
World Mutation
 ↓
Verification
 ↓
New State
```

Нельзя считать:

```text
intent = done
```

только потому, что DecisionHub его выбрал.

---

# 4. Commitment Contract

После выбора действия NPC должен получить **явное обязательство на выполнение**.

Например:

```text
Intent:
EAT

Commitment:
TASK-EAT-123

Target:
TAVERN_TABLE_4

Status:
COMMITTED

Required capabilities:
CAN_MOVE
CAN_REACH
CAN_INTERACT
```

Статусы:

```text
PROPOSED
COMMITTED
EXECUTING
BLOCKED
INTERRUPTED
COMPLETED
FAILED
EXPIRED
CANCELLED
```

Это должно быть runtime state, а не текстовая пометка.

---

# 5. Запрет stale intent

Особенно важно устранить класс:

> NPC решил сделать A, затем система продолжила исполнять старый B.

Каждая новая committed action должна либо:

1. заменить предыдущий совместимый intent;
2. продолжить существующий task;
3. явно прервать старый task;
4. быть отвергнута как несовместимая.

Никакое старое:

```text
MOVE
TALK
FOLLOW
PATROL
```

не должно продолжаться после принятия несовместимого commitment:

```text
SLEEP
EAT
WORK
REST
```

без explicit policy.

---

# 6. Action Ownership

Для каждого активного поведения должен быть установлен:

```text
current_action_owner
```

или эквивалентный механизм.

Например:

```text
MOVE_TO_HOME
```

владеет movement execution.

```text
TALK_TO_NPC
```

владеет dialogue execution.

```text
EAT
```

владеет interaction/execution.

Нельзя, чтобы одновременно существовало:

```text
MOVE_TO_HOME
+
PATROL
+
TALK_TO_NPC
```

как три независимых executor'а.

Если многозадачность понадобится позже, она должна быть сознательной архитектурой с приоритетами, а не побочным эффектом нескольких систем.

---

# 7. Action Interrupt Contract

Любое действие должно иметь возможность быть:

```text
COMPLETED
INTERRUPTED
FAILED
```

Причины interruption:

```text
new higher-priority physiological need
injury
target disappeared
target inaccessible
social interruption
player intervention
world event
explicit NPC reconsideration
```

Пример:

```text
NPC идёт домой
↓
sleep pressure становится critical
↓
NPC переоценивает состояние
↓
MOVE_HOME interrupted
↓
REST/SLEEP committed
```

Это не должно происходить через ручной `if`.

Необходим общий механический контракт.

---

# 8. Action Verification

После `Execution` система обязана проверить:

> произошло ли то, ради чего действие было предпринято?

Например:

```text
Intent = EAT
```

не означает:

```text
hunger -= 20
```

пока NPC действительно:

* дошёл до ресурса;
* получил доступ;
* выполнил interaction;
* потребил пищу.

Только после этого:

```text
ExecutionResult = SUCCESS
```

и появляется соответствующий `StateDelta`.

Если путь был заблокирован:

```text
ExecutionResult = FAILED
```

а не:

```text
NPC thinks he ate
but hunger mysteriously decreased
```

---

# 9. Action/Intent Coherence Invariant

Добавить обязательный Stage 2 invariant:

### ST2-ACTION-01

> После успешного принятия Intent фактический runtime behavior должен перейти в execution path этого Intent в течение установленного bounded horizon.

Нельзя иметь:

```text
Intent = SLEEP
Activity = WALK
```

дольше разрешённого transition window без explicit explanation.

---

# 10. Action/State Coherence

Добавить проверки:

### ST2-ACTION-02

Если:

```text
activity = EAT
```

должно существовать:

```text
EAT task / commitment / execution context
```

### ST2-ACTION-03

Если:

```text
activity = SLEEP
```

NPC должен находиться в валидном sleep context.

### ST2-ACTION-04

Если:

```text
activity = TALK
```

должен существовать:

```text
conversation/session/interaction target
```

### ST2-ACTION-05

Если:

```text
activity = MOVE
```

должен существовать:

```text
movement target / path / traversal task
```

### ST2-ACTION-06

Не должно существовать:

```text
activity = X
```

при фактическом execution state:

```text
Y
```

если X и Y не являются допустимыми фазами одного процесса.

---

# 11. Stale Task Detection

Ввести диагностический механизм:

```text
TaskStartedAt
TaskLastProgressTick
TaskExpectedCompletion
TaskLastWorldMutation
```

Если NPC:

```text
COMMITTED = EAT
```

но 20 тиков продолжает двигаться по старому маршруту без прогресса в EAT,

система обязана зарегистрировать:

```text
STALE_ACTION
```

а не продолжать симуляцию молча.

Это должно попасть в diagnostics и test infrastructure.

---

# 12. Movement должен подчиняться Action Commitment

Текущий симптом:

> NPC постоянно бегает из угла в угол

указывает на то, что movement способен существовать как самостоятельная инерционная активность.

Это необходимо изменить.

Movement должен быть:

```text
capability / executor
```

а не самостоятельной волей.

То есть:

```text
DECISION:
GO_HOME

↓
COMMITMENT:
MOVE_TO_HOME

↓
MOVEMENT EXECUTOR
```

а не:

```text
movement scheduler
```

сам решает, что NPC снова должен куда-то идти.

---

# 13. Запрет perpetual movement

NPC не должен иметь бесконечное:

```text
MOVE → new MOVE → new MOVE → new MOVE
```

без причины.

Каждое движение должно иметь:

```text
purpose
target
termination condition
```

Примеры:

```text
MOVE_TO_WORK
MOVE_HOME
MOVE_TO_FOOD
MOVE_TO_FRIEND
FLEE
EXPLORE
PATROL
FOLLOW
```

После достижения target:

```text
MOVEMENT COMPLETED
```

NPC должен оказаться в:

```text
settled state
```

или запросить новое решение.

---

# 14. Settled / Idle State

Stage 2 должен ввести полноценное понятие:

> **NPC может ничего не делать.**

Это очень важно.

В нынешнем поведении существует опасный implicit assumption:

```text
NPC exists
→ NPC must continuously produce visible activity
```

Это неверно.

Реальный человек:

* стоит;
* сидит;
* смотрит;
* думает;
* ждёт;
* отдыхает;
* наблюдает;
* скучает;
* работает внутри помещения;
* ничего не делает.

Поэтому:

```text
IDLE
```

не является ошибкой.

Это полноценное состояние мира.

---

# 15. Social Chatter Problem

Вторая наблюдаемая проблема:

> NPC постоянно разговаривают друг с другом, практически каждую секунду.

Это тоже не следует исправлять простым:

```text
conversation_probability = 0.1
```

Потому что проблема не только в вероятности.

У тебя отсутствует полноценная модель:

> **почему сейчас разговор вообще социально уместен?**

---

# 16. Conversation Opportunity Gate

Ввести:

```text
ConversationOpportunity
```

или эквивалентный доменный механизм.

Диалог возможен только если существует достаточное основание:

```text
PROXIMITY
+
SOCIAL_RELATION
+
ATTENTION
+
OPPORTUNITY
+
MOTIVE
```

Примеры мотивов:

```text
greeting
question
request
information
gossip
conflict
trade
affection
comfort
warning
shared_activity
```

Без мотива:

```text
NPC_A → NPC_B
```

не должен генерировать бесконечный разговор только потому, что они находятся рядом.

---

# 17. Conversation Cooldown

После завершения социального exchange должен существовать cooldown / refractory period.

Например концептуально:

```text
conversation ended
↓
social cooldown
↓
attention disperses
↓
new opportunity may emerge
```

Размер cooldown не должен быть одной глобальной константой.

Он может зависеть от:

```text
relationship
topic
urgency
personality
social environment
recent interaction
```

Но базовый механизм должен существовать уже в Stage 2.

---

# 18. Turn-Based Conversation Contract

Разговор не должен быть:

```text
NPC A speaks
NPC B immediately speaks
NPC A immediately speaks
NPC B immediately speaks
...
```

без состояния диалоговой сессии.

Необходимо иметь:

```text
ConversationSession
    participants
    topic
    initiator
    current_turn
    last_exchange_tick
    reason
    termination_condition
```

После реплики должна существовать возможность:

```text
RESPOND
IGNORE
LEAVE
CHANGE_TOPIC
END
```

Отсутствие ответа — валидное решение.

---

# 19. Conversation Termination

Каждая социальная сессия должна иметь termination conditions.

Например:

```text
topic exhausted
information exchanged
participant leaves
participant distracted
participant loses interest
social goal achieved
conflict escalates
time pressure
higher-priority need
```

Если ни одно из условий не выполняется, система не должна бесконечно создавать реплики.

---

# 20. Conversation Frequency

Добавить агрегированный diagnostic metric:

```text
speech_rate_per_npc_hour
```

а также:

```text
conversation_count
conversation_duration
average_gap_between_interactions
repeat_pair_rate
```

Это необходимо потому, что:

> «NPC говорит слишком много»

не является субъективным bug report после введения метрик.

Он должен превращаться в численную характеристику поведения мира.

Например:

```text
NPC hour:
20 conversations
```

и:

```text
NPC hour:
3 200 utterances
```

— это совершенно разные классы симуляции.

---

# 21. Speech не равен Thought

LLM narration/dialogue должна рассматриваться как:

```text
decision to communicate
↓
speech act
↓
verbalization
```

а не:

```text
NPC active
→ generate dialogue
```

Это особенно важно для будущего LLM слоя.

LLM не должна сама решать:

> «NPC сейчас хочет ещё что-нибудь сказать».

Сначала Python должен принять решение:

```text
COMMUNICATE
```

и только потом LLM формулирует содержание.

---

# 22. Social Activity Budget

Ввести мягкий ресурс:

```text
social_attention
```

или эквивалентный derived budget.

Он может учитывать:

* fatigue;
* current task;
* social interest;
* relationship;
* recent conversation;
* urgency;
* environment.

Не делать:

```text
social_budget = 3 conversations/day
```

как жёсткое правило.

Цель:

> **сделать разговор поведением с opportunity cost.**

Если NPC разговаривает:

```text
он не просто «генерирует текст»,
он тратит время,
внимание,
социальную энергию,
```

и тем самым конкурирует с:

* работой;
* отдыхом;
* едой;
* движением;
* наблюдением.

Это приблизит NPC к настоящей жизни.

---

# 23. Group Formation

Отдельно проверить текущую логику, из-за которой NPC:

```text
сходятся
→ образуют группу
→ начинают говорить
→ остаются группой
→ снова говорят
```

Группа не должна быть липким состоянием.

Должны существовать:

```text
formation cause
membership rationale
group activity
dispersion cause
```

NPC не должен находиться в группе только потому, что когда-то попал в радиус другого NPC.

---

# 24. Anti-Flapping

После появления commitment нужно не допустить противоположной ловушки:

```text
MOVE
→ EAT
→ MOVE
→ TALK
→ MOVE
→ SLEEP
→ TALK
→ MOVE
```

каждый тик.

Ввести минимальную:

```text
commitment stability window
```

и/или:

```text
action switching cost
```

Переключение должно происходить, когда:

* действие завершено;
* действие стало невозможно;
* появился sufficiently stronger competing pressure;
* произошло событие, которое действительно меняет решение.

---

# 25. Priority Arbitration

Если одновременно:

```text
hunger = high
fatigue = high
friend nearby
work deadline
```

NPC не должен запускать четыре действия.

Нужен один arbitration step:

```text
candidate pressures
↓
priority / evaluation
↓
ONE active commitment
```

Будущая сложная мотивация заменит простой priority model, но уже сейчас должна существовать **одна точка разрешения конфликта**.

# 28. Новые Stage 2 Invariants

Добавить к предыдущим 20:

### ST2-ACTION-07

Every active NPC activity has an owning commitment/task.

### ST2-ACTION-08

A new incompatible commitment explicitly interrupts or supersedes the previous commitment.

### ST2-ACTION-09

No stale movement continues after an incompatible action commitment.

### ST2-ACTION-10

Successful intent requires execution evidence.

### ST2-ACTION-11

Failed execution does not produce successful world-state effects.

### ST2-ACTION-12

Every movement has purpose, target, or explicit movement mode.

### ST2-ACTION-13

Movement can terminate.

### ST2-ACTION-14

Idle/settled state is valid.

### ST2-ACTION-15

NPC cannot have multiple conflicting active commitments unless explicitly supported by an approved concurrency model.

### ST2-SOC-01

Conversation requires an opportunity.

### ST2-SOC-02

Conversation has an explicit reason/motive.

### ST2-SOC-03

Conversation has a bounded session state.

### ST2-SOC-04

Conversation can terminate.

### ST2-SOC-05

Speech cannot be emitted without a communication decision.

### ST2-SOC-06

Repeated conversation requires a new valid opportunity.

### ST2-SOC-07

Group membership has a formation cause.

### ST2-SOC-08

Group membership can terminate.

### ST2-SOC-09

NPC may remain silent when no communication motive exists.

### ST2-SOC-10

NPC social activity consumes time/attention and competes with other activities.

# 29. Архитектурный смысл исправлений

Эти исправления нужны не ради того, чтобы NPC:

> «перестали бегать и болтать».

Они нужны для гораздо более важного результата:

> **поведение NPC должно иметь причинную инерцию, завершение и стоимость.**

Тогда:

```text
NPC решил есть
```

означает:

> он действительно начал есть или попытался это сделать.

```text
NPC решил говорить
```

означает:

> у него существует причина вступать в социальный обмен.

```text
NPC решил идти
```

означает:

> он куда-то идёт, а не просто производит бесконечную анимацию движения.

# 31. Definition of Done Stage 2 — расширенный

Stage 2 не считается закрытым, пока система не демонстрирует:

## LIFE

NPC способен:

```text
wake
→ work
→ hunger
→ seek food
→ obtain food
→ eat
→ continue life
→ fatigue
→ seek rest
→ sleep
→ recover
```

## ACTION

При принятии действия:

```text
INTENT
→ COMMITMENT
→ EXECUTION
→ RESULT
```

и фактическое runtime behavior соответствует выбранному действию.

## STOP

NPC умеет:

```text
finish action
→ stop
→ remain idle / settle
```

и не обязан всё время перемещаться.

## SOCIAL

NPC:

* не говорит каждую секунду;
* не обязан отвечать;
* может игнорировать;
* может закончить разговор;
* может просто находиться рядом с другим NPC молча;
* может работать рядом с другим NPC без постоянного диалога;
* вступает в разговор при наличии причины.

## CAUSALITY

Для каждого значимого поведения можно проследить:

```text
CAUSE
→ INTERNAL STATE
→ DECISION
→ COMMITMENT
→ EXECUTION
→ WORLD CONSEQUENCE
→ NEW STATE
```

# 32. Ключевой переход

После исправления этих проблем Stage 2 должен изменить не только набор параметров, но **сам характер NPC**.

До Stage 2:

```text
NPC
= генератор действий
```

После Stage 2:

```text
NPC
= организм,
который живёт во времени,
занимается делами,
может устать,
останавливаться,
ждать,
испытывать потребности,
пытаться их удовлетворять,
ошибаться,
не успевать,
прерываться
и самостоятельно выбирать,
чем заняться дальше.
```

И только после этого имеет смысл переходить к Stage 3 — **Perception / Observation**.

Потому что дальнейшая цепочка должна быть:

```text
STAGE 0
единая истина
        ↓
STAGE 1
единая причинность
        ↓
STAGE 2
единая деятельность + телесная жизнь
        ↓
STAGE 3
личное восприятие
        ↓
STAGE 4
личная картина мира
        ↓
STAGE 5
аффект + мотивация
        ↓
STAGE 6
автобиографическое Я
        ↓
STAGE 7
планирование
        ↓
STAGE 8
отношения
        ↓
STAGE 9
роли + экономика
        ↓
STAGE 10
нормы + культура
```

Главный критерий Stage 2:

> **NPC должен перестать выглядеть как объект, которому постоянно надо выдавать следующую анимацию, и начать выглядеть как человек, у которого есть текущее дело, причина его делать, возможность его завершить и возможность ничего не делать.**
