## Проблема 1. BLOCKER CI: импорт llama-server роняет ВСЮ подборку тестов на стадии collection

### Симптом
В GitHub Actions (`.github/workflows/test.yml`, job `test`, `runs-on: ubuntu-latest`, шаг
`python -m pytest tests/ --tb=short --junitxml=test_results.xml`) пайплайн падает ещё до запуска
тестов: `ERROR collecting ... Interrupted: 1 error during collection`. Реальные тесты не выполняются
вовсе, отчёт `test_results.xml` бесполезен, мояpy-шаги до дела не доходят.

### Источник
`backend/tests/sandbox/SUPERBOX/scenarios/cognition_p3d_test.py` — код поднятия LLM выполняется
**на уровне модуля** (а pytest собирает файл, т.к. имя подходит под дефолтный паттерн `*_test.py`;
в `backend/pytest.ini` опция `python_files` НЕ переопределена):

```python
48  try:
52      from scripts.llm_server_manager import kill_llama_server, start_llama_server
54      if not start_llama_server():
55          print("[G0] ⚠ LLM не поднялась — семантика MOVE резолвится fast-path")
56      atexit.register(kill_llama_server)
57  except ModuleNotFoundError as _e:      # ← ловится ТОЛЬКО отсутствие модуля
58      print(f"[G0] llm_server_manager недоступен ({_e})")
```

`scripts/llm_server_manager.py::start_llama_server` (строки 43–71) вызывает
`subprocess.Popen([settings.llama_cpp_server_executable, ...])` **без `except`** (только
`try/finally` для закрытия файла stderr). Бинажник по умолчанию — windows-путь:

```python
# backend/app/core/config.py:64-66
llama_cpp_server_executable: str = str(BASE_DIR / "Models LLM" / "llama" / "llama-server.exe")
```

На раннере (`ubuntu-latest`, модель `Models LLM/...llama-server.exe` в репозиторий не коммитится)
`Popen` бросает `FileNotFoundError`, который НЕ является `ModuleNotFoundError` → вылет из
модуля collection-фазы.

### Репродукция (проверено локально, Windows)
```powershell
$env:AIDM_LLAMA_CPP_SERVER_EXECUTABLE='C:\nonexistent_dir_ci\llama-server.exe'
cd backend; ..\.venv\Scripts\python.exe -m pytest tests/sandbox/SUPERBOX/scenarios/cognition_p3d_test.py --collect-only -q
# ERROR collecting tests/sandbox/SUPERBOX/scenarios/cognition_p3d_test.py
# E   FileNotFoundError: [WinError 2] Не удается найти указанный файл
# !!!!!!!!!!!!!!!!!!! Interrupted: 1 error during collection !!!!!!!!!!!!!!!!!!!
```
Префикс переменных окружения — `AIDM_` (`backend/app/core/config.py:180`), это важно для ручных
прогонов.

### Побочный эффект той же конструкции (тоже баг)
На машине разработчика, где `llama-server.exe` есть, **один только сбор тестов** поднимает реальный
7B-сервер (`Qwen2.5-7B-Instruct-...gguf`) и снимает его через `atexit`, а `pytest --collect-only`
тратит ~5–9 с и создаёт `backend/logs/llama_server_stderr.log`. Сбор тестов не должен иметь таких
побочных эффектов.

### Второй носитель того же анти-паттерна
`backend/tests/IPT.py:29-36` — идентичный `try/except ModuleNotFoundError` + `start_llama_server()`
на уровне модуля. В default-подборку не попадает (имя не matches `test_*.py`/`*_test.py`), но
ломает любой прогон, где его собирают/импортируют явно, и ведёт себя так же при `FileNotFoundError`.

### Что предлагается сделать (на выбор, по убыванию предпочтительности)
1. **Не запускать LLM на уровне модуля.** Перенести поднятие сервера в fixture с
   `pytest.skip(..., allow_module_level=True)` / `@pytest.mark.skipif(...)` по предикату
   «бинарник существует и исполняем»: `Path(settings.llama_cpp_server_executable).is_file()`
   (+ `os.access(..., os.X_OK)` на POSIX) либо `shutil.which(...)`.
2. Как минимум — расширить `except` до `except (ModuleNotFoundError, OSError)`
   (`FileNotFoundError`/`PermissionError` наследуются от `OSError`), и то же в `IPT.py`.
   Это снимет блок CI, но оставит 5–9 с и поднятие LLM при collection.
3. Стратегически — вынести sandbox/SUPERBOX-сценарии из default-подборки
   (отдельный marker, например `@pytest.mark.external_llm`, плюс `-m "not external_llm"` в CI;
   либо `collect_ignore`/`testpaths`), и добавить в CI job явный guard-шаг на наличие бинарника.

Дополнительно стоит проверить: не падают ли аналогичным импортом и другие файлы sandbox
(поиск по репозиторию: `start_llama_server`).

## Проблема 2. `test_tick_orchestrator_full_loop` — дельты Фазы 8 не доходят до NPC (и нестабильный крах reaction-обработчика)

### Симптом
Тест `backend/tests/test_tick_orchestrator_full_loop.py` красный: ожидаемый рост `psyche.stress`
у NPC после события `PLAYER_ATTACKS` не происходит (`final stress: 30.0` при стартовых 30.0).
Регрессией последних коммитов не является — тест разъехался с текущим контрактом API плюс показывает
продуктовую проблему в Фазе 8.

### Установленные факты (проверено временным зондом, который печатал состояние внутри Фазы 8)
1. **`ctx.all_npcs_raw` пуст в Фазе 8.** Оркестратор НЕ берёт NPC откуда-то ещё, кроме параметра
   `execute(..., all_npcs_raw=...)`: он пробрасывается в `create_tick_context`
   (`backend/app/services/tick_orchestrator.py:611` и `:641`). Тест параметр не передаёт, а мок
   `life_engine.get_npc_states` в `all_npcs_raw` не попадает. Это контракт S113
   («Явная передача NPC, включая аватара») — тест ему больше не соответствует.
2. **Запись NPC без `location_id` отсеивается фильтром по текущей локации**
   (`_current_loc = ctx.scene_state.get("location_id", "")`, `tick_orchestrator.py:823`/`:1112`).
   После добавления `"location_id": "test_room"` в фикстуру NPC доходит до Фазы 8 — подтверждено
   зондом (`[SPY] ctx.all_npcs_raw: dict id= npc_1 ...`).
3. **Атака разрешается как промах**: `combat_data={'npc_1': {'miss': True, 'distance': 999.0,
   'max_range': 1.8}}`. В `scene_state["npc_positions"]` есть только `npc_1`, позиции игрока нет →
   дистанция считается как «неизвестна/далеко» (999) → нет физических дельт, нет шока.
4. **Проверка «через мок» ненадёжна**: `life_engine_mock.get_npc_states("test_campaign")[0] is npc_raw`
   дало `False` — элемент списка, возвращаемого моком, в ходе тика подменяется другой структурой.
   Утверждать надо по собственной ссылке на словарь NPC, а не через `get_npc_states`.
5. **Продуктовый след (важнее самого теста).** В прогоне периодически появляются строки:
   ```
   WARNING [PHASE8_CRASH] handler=reaction error=AttributeError: 'Phase8Context' object has no attribute 'scene_state'
   ERROR   [PHASE_8] reaction handle() failed: 'Phase8Context' object has no attribute 'scene_state'. Events lost this tick.
   ```
   То есть подписчик когнитивного слоя падает внутри изолятора `_execute_handler`
   (`backend/app/services/phases/reduction.py:221-231`) и **события теряются в этом тике** —
   тихая потеря данных в рантайме, а не только в тесте. Крах нестабилен (не в каждом прогоне).

   Кандидат-виновник: `backend/app/services/events/reaction_subscriber.py:232`
   ```python
   scene_state=ctx.shared_context.scene_state,   # единственный незащищённый доступ в этом слое
   ```
   для сравнения — сосед по слою делает правильно
   (`backend/app/services/events/social_input_projector.py:96`, `:114`):
   ```python
   scene_state=getattr(ctx.shared_context, "scene_state", None) or ctx.tick_ctx.scene_state or {}
   ```
   `Phase8Context` (`backend/app/models/phase8.py:34`) поля `scene_state` не имеет вообще;
   есть `all_npcs_raw`, `all_npc_contexts`, `shared_context: Any`, `campaign_id`, `tick_ctx`,
   `physical_deltas_materialized`. `shared_context` — `Any`, поэтому mypy такое не ловит.
   Контекст: `reduction.py:176-201` создаёт fallback-`SimpleNamespace(scene_state, campaign_id)`
   и дописывает `spatial_query` **только если `shared_context is None`**; если объект существует,
   но нужных полей в нём нет — подписчики падают (исторически это уже лечили: `BUG-CORE-007`,
   `PHASE8-SOCIAL-CID FIX` в тех же строках).

   Оговорка честно: мой зонд, обёртывавший `ReactionSubscriber.handle`, это исключение не
   перехватил — значит трейс либо из другой ветки/повторного (idle-)прохода, либо из вложенного
   вызова. Локализовать нужно трейсом, а не догадками (рецепт ниже).

### Как локализовать за 10 минут (рецепт)
Временно создать `backend/tests/_tmp_probe_loop.py`, скопировав тело теста из
`test_tick_orchestrator_full_loop.py`, и добавить два инструмента:
```python
# 1) передать NPC по текущему контракту (S113) + location_id/позицию игрока в сцене
result = orchestrator.execute(campaign_id="test_campaign", scene_state=scene, tick_number=1,
                              all_npcs_raw=[npc_raw])

# 2) перехватить реальный трейс падения Фазы 8
import app.services.events.reaction_subscriber as rs
_orig = rs.ReactionSubscriber.handle
def _spy(self, events, ctx):
    try:
        return _orig(self, events, ctx)
    except Exception:
        import traceback; print("".join(traceback.format_exc())); raise
rs.ReactionSubscriber.handle = _spy
```
Прогон:
```powershell

..\.venv\Scripts\python.exe -m pytest tests/_tmp_probe_loop.py -q -s --log-cli-level=WARNING
```
Файл — временный, удалить после диагностики (в репозитории его быть не должно).

### Что предлагается сделать
1. Сначала починить пункт 5 (продукт): незащищённые обращения к `ctx.shared_context.<поле>` в
   подписчиках Фазы 8 привести к `getattr(..., None)`-паттерну, либо добавить `scene_state` в
   `Phase8Context` и заполнять его в `_execute_handler`. Это вернёт потерянные события и, вероятно,
   само по себе сдвинет стресс в тесте.
2. Затем привести фикстуру теста к текущему контракту: явный `all_npcs_raw`, `location_id` у NPC,
   позиция «игрока» в `npc_positions` (иначе `miss / distance=999` и физические дельты не появятся),
   утверждения — по прямой ссылке на словарь NPC.
3. Сформулировать, что именно за инвариант: «дельты Фазы 8 → delta_buffer → применяются в Фазе 10»,
   и проверить, должен ли idle-тик с промахом вообще давать рост стресса у свидетеля
   (иначе тест проверяет не то).
