# ТЗ: Process Lifecycle Hygiene — «Игра выключена = всё её выключено»

> **Для:** Архитектор-сессия завтра (любой профиль, задача инфра-класса)
> **Приоритет:** Hygiene/P1 (не блокирует фичи, но засоряет системы пользователей)
> **От:** сессия Event Identity (археология инцидента — ниже)
> **Тип ADR:** вероятно STANDARD (инфраструктура, без онтологических сдвигов — решит исполнитель после своей археологии)

## 1. КОНТЕКСТ: оплаченный инцидент (нашёл Event Identity-сессия, 2026-09-25, ~00:35)

### 1.1. Что случилось

Во время рутинной операции «окно тишины перед тестовым прогоном» (протокол §3.12 РЕЖИМА РАБОТЫ) был обнаружен **живой production-бэкенд при выключенной игре**:

```
ProcessId 16952: .venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
ProcessId 21124: python3.13.exe (тот же uvicorn, реальный воркер)
StartTime: 23:50 | CPU воркера: 18.7 сек | WS: 58 МБ
```

Игра (Pygame-клиент) была **закрыта**. Backend продолжал жить: держал порт 8000, открытые SQLite-соединения к сейвам кампаний, воркеры async-слоя. Запущен в 23:50 — предположительно лаунчером при игровом запуске; при выходе из игры **не остановлен никем**.

### 1.2. Почему пользователь «не видит» процесс (корень UX-проблемы)

Пара оболочка/воркер — точное воспроизведение шрама S269 (Правила Фикса Багов, Часть XII):

| PID | Образ | Почему невидим |
|---|---|---|
| 16952 | `.venv\Scripts\python.exe`, WS 7 МБ, CPU ≈ 0 | обёртка-стартер; в Диспетчере задач выглядит как безликий «python», CPU = 0 → пользователь считает шумом |
| 21124 | `python3.13.exe` (WindowsApps-образ!), WS 58 МБ | **не называется «python.exe»** — пользователь, ищущий «python», его не найдёт |

WindowsApps-дистрибутив Python спавнит дочерние процессы под образом `python3.13.exe`. Ни пользователь, ни типовые проверки не связывают это с игрой.

### 1.3. Чем это опасно (не только «жрёт систему»)

1. **SQLite-гонки с тестами:** живой backend держит открытые соединения к сейвам; DriftLab/persistence-тесты копируют и пишут в те же каталоги → флиттерные ReadOnly-краши, INVALID-прогоны (класс отказов §3.12).
2. **Порт-конфликт 8000:** два backend'а (забытый + новый запуск игры) → `RuntimeError: Не удалось подключиться` / «два LLM-менеджера дерутся за один порт» — оплаченный отказ из §3.12.
3. **LLM-воркеры:** если сервер поднимал пул LLM-задач / соединение с llama-server — они умирают вместе с ним неконтролируемо.
4. **Портфель привидений:** рестарты игры наслаивают процессы; после недели использования — 3–4 «невидимых python3.13» в памяти.

### 1.4. Корневая причина (гипотеза, подтверждать археологией исполнителя)

Жизненный цикл backend **не связан** с жизненным циклом клиента:
- лаунчер поднимает uvicorn как независимый процесс (не job/child с привязкой к себе);
- нет graceful shutdown клиента → backend'у;
- нет watchdog: «клиента нет N минут → backend завершается»;
- `/api/health` отвечает, но никто не спрашивает «а есть ли ещё живой клиент».

**Запрещено верить гипотезе §1.4** — сначала археология: кто spawns uvicorn (game_launcher.py? main.py? отдельный скрипт?), как он отвязывается (DETACHED_PROCESS? shell=True?), есть ли существующие механизмы остановки (S217 упоминает работу с llama-server start/stop — прецедент там есть).

## 2. ЦЕЛЬ

Инвариант жизненного цикла: **последний живой потребитель ENIGMA-процессов закрыт → все процессы ENIGMA (backend uvicorn, llama-server, вспомогательные воркеры) завершены. Ни одного осиротевшего процесса.**

## 3. ТРЕБОВАНИЯ

### R1. Связывание жизненных циклов (основной механизм)
Backend uvicorn обязан запускаться в связке с лаунчером/клиентом одним из способов (выбрать по археологии, обосновать в ADR):
- **Job Object (Windows):** клиент создаёт Win32 Job с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` и помещает backend в него — смерть клиента (даже по крашу/убийству из Диспетчера) убивает backend. Каноническое Windows-решение;
- **или child-process с контролем:** клиент держит handle на backend и в finally/daemon-паттерне останавливает;
- **или watchdog:** backend пингует клиента (named pipe / heartbeat-файл с TTL); отсутствие пинга N минут → self-termination. Независим от способа запуска — покрывает и ручные запуски.

Допустима комбинация (Job для штатного запуска + watchdog для ручного/странного).

### R2. Симметрия llama-server
Тот же инвариант для llama-server (прецедент S217: старт/стоп уже реализован в менеджере моделей) — проверка, что он не остаётся жить после остановки backend (или наоборот): цепочка клиент → backend → llama-server должна схлопываться каскадом.

### R3. Диагностируемость осиротевших процессов
`/api/health` (или новый эндпоинт) + лог старта backend обязаны писать **pid-файл** (каталог сейвов или runtime): `{pid, started_at, parent_pid, port}`. Это превращает будущие инциденты из «чайного сеанса Get-CimInstance» в чтение одного файла. Устаревший pid-файл (процесс мёртв) — самоочищается при старте.

### R4. Graceful shutdown по REST-команде
Эндпоинт `POST /api/shutdown` (только localhost): сервер корректно завершает пулы, коммитит/закрывает SQLite, останавливает llama-server, пишет в лог. Пользователю — кнопка «Завершить работу» в настройках/лаунчере (прецедент UI S217: модалка выхода уже существует).

### R5. Защита от дурака при тестах (для нас самих)
Preflight тестовых прогонов (DriftLab, pytest с persistence): перед стартом проверять живой backend на порту 8000 / pid-файл → предупреждение или автозапрос остановки. Закрывает класс флиттерных отказов §3.12 по нашей вине.

## 4. ТАБУ (запреты)

- ❌ Убийство процессов «по имени python*» без идентификации (шрам S269: python3.13.exe ≠ python.exe; заглушка-обёртка WS 7–13 МБ CPU≈0 — легитимная часть пары, не цель);
- ❌ `taskkill /im python.exe /f` в лаунчере/скриптах — только по pid из pid-файла или по собственному child-handle;
- ❌ Watchdog, убивающий backend при первом пропущенном пинге (гистерезис: N пропусков, N минут);
- ❌ Асинхронный self-kill из воркер-потока backend (только main-thread, прецедент ADR-O-364 outbox-дисциплины);
- ❌ Скрытые except при остановке (L4: тихий отказ shutdown = процесс-зомби снова).

## 5. ГЕЙТЫ ПРИЁМКИ

1. **Сценарий «игра выключена»:** запустить игру через лаунчер → выйти штатно → `Get-CimInstance` по pid-файлу: 0 процессов ENIGMA. **GREEN-критерий главного инварианта.**
2. **Сценарий краша клиента:** убить клиент из Диспетчера задач (Job Object должен отработать) → backend мёртв в течение grace-периода.
3. **Сценарий двойного запуска:** второй запуск игры при живом backend → либо переиспользование, либо контролируемый рестарт — но **не** два сервера на порту.
4. **Сценарий ручного запуска backend** (run_terminal_dm-стиль) без клиента → watchdog завершает его после таймаута (настраиваемо, для разработки — отключаемо env-флагом).
5. IPT-зона: инвариант не симуляционный, IPT-добавление **не требуется**; вместо этого — скрипт `scripts/check_orphans.py` (по pid-файлам: живы ли заявленные, есть ли неучтённые uvicorn/llama-server) — в CI по желанию, локально — в hygiene-чеклист.
