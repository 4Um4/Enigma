# ENIGMA — Протокол Фикса Багов и Архитектурного Дрейфа

**Статус:** Исполняемый протокол. Нарушение = архитектурный баг.
**Область применения:** Любой фикс в `backend/` или `frontend/`, изменяющий pipeline, DTO, ownership или источник истины.

---

## ЧАСТЬ 0 — Абсолютное правило

**Симптом не является причиной.**

Запрещено:
- NPC не подошёл → менять `MovementEngine`
- NPC исчез → менять `Frontend`
- `tuple unpack error` → менять `return`

**Если причинная цепь не восстановлена — ФИКС ЗАПРЕЩЁН.**

Цель — найти **ПЕРВЫЙ отказавший узел** pipeline. Не исправить симптом.

## ЧАСТЬ I — Кэш является призраком

Если изменялись: dataclass, DTO, enum, imports, contracts, сигнатуры, удаление полей — обязательно очистить `__pycache__`.

### Очистка (Linux / macOS)

```bash
find backend/ -type d -name "__pycache__" -exec rm -rf {} + 2>/dev/null
find frontend/ -type d -name "__pycache__" -exec rm -rf {} + 2>/dev/null
find . -name "*.pyc" -delete 2>/dev/null

python -m compileall backend frontend
```

### Очистка (Windows PowerShell)

```powershell
Get-ChildItem -Path "backend/" -Filter "__pycache__" -Recurse -Directory | Remove-Item -Recurse -Force
Get-ChildItem -Path "frontend/" -Filter "__pycache__" -Recurse -Directory | Remove-Item -Recurse -Force
Get-ChildItem -Path "." -Filter "__pycache__" -Recurse -Directory | Remove-Item -Recurse -Force
Get-ChildItem -Path "." -Filter "*.pyc" -Recurse -File | Remove-Item -Force
Get-Process python -ErrorAction SilentlyContinue | Stop-Process -Force

python -m compileall backend frontend
```

**Скрипт-помощник:** `scripts/clean_cache.ps1` (Windows).
http://localhost:8000/health - помощник проверки здоровья llm и MVP

## ЧАСТЬ III — Causal Topology

Построить поток:

```
CREATE → READ → TRANSFORM → MATERIALIZE → APPLY → COMMIT → PROJECT → PRESENT
```

Вывести:

```
SOURCE:           (кто создаёт объект)
READERS:          (кто читает)
WRITERS:          (кто пишет — должен быть один)
COMMIT_STAGE:     (где объект персистится)
PROJECTION_STAGE: (где объект проецируется в snapshot)
```

---

## ЧАСТЬ IV — Single Source of Truth

Не путать **MULTIPLE REPRESENTATIONS** (допустимо) с **DOUBLE TRUTH** (критический баг).

**MULTIPLE REPRESENTATIONS** — допустимо, если downstream только читает:
```
Editor JSON → RuntimeState → Snapshot → Frontend
```

**DOUBLE TRUTH** — только если:
- SOURCE A пишет значение X
- SOURCE B пишет значение Y
- Доказано: `A.x != B.x`

Если доказательства нет → **MULTIPLE REPRESENTATIONS** (НЕ баг).
Если доказательство есть → **DOUBLE TRUTH DETECTED** (CRITICAL).

## ЧАСТЬ VI — Contract

Проверить:
- `input` (что принимает функция)
- `output` (что возвращает)
- `caller expectation` (что ожидает вызывающий)

Если ожидание ≠ фактическому контракту → **BOUNDARY VIOLATION**.

## ЧАСТЬ VII — Architectural Charter

Проверить чек-лист:

- [ ] immutable snapshot (тике)
- [ ] temporal isolation (`game_time_seconds` — единственный источник)
- [ ] authoritative source (один SSOT на домен)
- [ ] DecisionHub — only scorer (не мутатор)
- [ ] отсутствие pipeline bypass
- [ ] отсутствие circular dependency
- [ ] отсутствие raw structures (только DTO)
- [ ] отсутствие partial commit

**Важно:** Если найдено нарушение — ответить:

```
AFFECTS_CURRENT_BUG: YES / NO
```

Если `NO` → **TECH_DEBT_NOTE** (записать, НЕ чинить в этом фиксе).

## ЧАСТЬ VIII.5 — Runtime Data Archaeology (Обязательный протокол)

Если pipeline-объект существует, но данные не доходят до конца:

- **НЕ УГАДЫВАТЬ** структуру данных.
- **НЕ ПРЕДПОЛАГАТЬ** имена ключей.

**Обязательный шаг:** внедрить `print()`-диагностику в точке CREATE или TRANSFORM.

### Правила диагностики

1. **Использовать ТОЛЬКО `print()`** — не `logger.info()`. Logger может быть выключен, `print()` виден всегда.
2. Диагностика должна показывать:
   - `type()` объекта
   - `len()` если это коллекция
   - `list(dict.keys())[:15]` — список реальных ключей
   - конкретные значения критических полей
3. **Итеративное погружение:**
   - Шаг 1: показать топ-ключи объекта
   - Шаг 2: показать ключи вложенного объекта (если нужен доступ)
   - Шаг 3: показать конкретные значения
4. Каждый шаг — запуск игры, чтение лога, уточнение диагноза.
5. Фикс пишется **ТОЛЬКО** после того как диагностика показала РЕАЛЬНУЮ структуру данных.

### Формат диагноза

```python
print(f"[DIAG_TAG] type={type(obj).__name__}, count={len(obj)}, keys={list(obj.keys())[:15]}")
```

### Пример (реальный кейс S55)

```
all_npcs_raw = list[dict] с ключами ['_version', '_type', 'tier', 'drives', 'psyche', ...]
  → psyche = dict с ключами ['willpower', 'breakpoint', 'loyalty_true', 'state', 'stress']
  → state = string "alert" (не dict!)
  → initiative_suppression = ОТСУТСТВУЕТ в npc_positions
```

Без этого протокола был бы написан фикс, читающий `body_state.pain`, которого **НЕ СУЩЕСТВУЕТ** в рантайме.

**ЗАПРЕТ:** Предлагать фикс, читающий ключи, которые НЕ были подтверждены `print()`-диагностикой в рантайме.

## ЧАСТЬ IX.5 — Confidence Calibration

**Вероятность запрещено выводить из интуиции.**

Допустимые источники:
- наблюдаемый лог
- assertion
- traceback
- runtime state
- process state
- contract mismatch
- CDS signal

**Запрещено:** `is_available=False` → «сервер не запущен (90%)».

Если отсутствуют прямые наблюдения → **MAX_PROBABILITY: 60%**
Если отсутствуют runtime-доказательства → **MAX_PROBABILITY: 40%**

Вероятность >80% допустима только при:
- [ ] воспроизводимом сценарии
- [ ] ИЛИ прямом логе
- [ ] ИЛИ найденном писателе состояния

## ЧАСТЬ X — Root Cause Validation

```
ROOT_CAUSE_CONFIDENCE: 0–100
```

| Диапазон | Разрешено | Запрещено |
|----------|-----------|-----------|
| **0–40** | логирование, assertions, trace | фикс, ADR, рефакторинг |
| **40–80** | локальная проверка, временный trace | изменение ownership, изменение pipeline |
| **80–100** | фикс | — |

## ЧАСТЬ XI — Fix Scope

Приоритет (от наименьшего вмешательства к наибольшему):

1. **локальный фикс** (1 функция / 1 метод)
2. **adapter** (обёртка)
3. **service** (логика сервиса)
4. **DTO** (контракт)
5. **ADR** (запись в `docs/ADR (Architecture Decision Records).md` + `docs/audits/ADR-0XX_IMPACT.md`)

**Запрещено:** изменять уровень выше, если уровень ниже не доказан невозможным.

Вывести:

```
FIX_SCOPE:  (1–5)
FILES:      (список файлов для изменения)
```


### Structured logging

**Запрещено:** `[LIFE] error` (нет контекста).

## ЧАСТЬ XIII — Smoke Test

После любого фикса:

1. **Пустой вход** — функция не падает на `None`/`[]`/`{}`.
2. **Реалистичный вход** — корректный результат.
3. **Boundary:** `None`, `[]`, `0`, `1`, `-1`, пустая строка.
4. **Тип результата** — соответствует контракту.
5. **Side effects** — `delta_buffer` / `scene_state` мутируются предсказуемо.

## ФИНАЛЬНОЕ ПРАВИЛО

Если LLM не может нарисовать:

```
создание → движение → изменение → применение → сохранение → проекция
```

— значит LLM не понимает баг.

Если LLM предлагает: ADR, рефакторинг, удаление слоя, изменение ownership — при `ROOT_CAUSE_CONFIDENCE < 80` — значит LLM нарушила протокол.

## 1. Invariant Probe Tests (IPT) — быстрая проверка ДО фикса

**Файл:** `backend/tests/IPT.py`
**Время:** ~5–60 секунд (зависит от числа инвариантов; в наборе уже ~46 инвариантов, включая AST-линтеры).
**Зависимости:** не требует сети; часть инвариантов диалогов требует LLM (при отсутствии LLM выводится предупреждение, инварианты без LLM работают).

**Назначение:** Проверка инвариантов симуляции **до коммита**. Слой «ДО» — запускается перед началом фикса, чтобы убедиться, что baseline не сломан. Если IPT красный — чинить нельзя, сначала восстанови baseline.

**⚠️ ПРАВИЛО ВЫВОДА (обязательно для LLM-архитектора):**
Итоговая суть IPT пишется В КОНЦЕ вывода — строка `ИТОГО: X passed / Y failed` и список 🔴 КРИТИЧНЫХ НАРУШЕНИЙ. Полный вывод сотен строк читать/показывать запрещено. Запускать тест целиком, а выводить **только последние 3–10 строк**:

```powershell
python backend/tests/IPT.py 2>&1 | Select-Object -Last 10
```

Если итог красный — перезапустить с фильтром ошибок (см. шапку `backend/tests/IPT.py`):

```powershell
python backend/tests/IPT.py 2>&1 | Select-String -Pattern "🔴|ИТОГО|Traceback|Error|Exception" -Context 0, 3
```

Это НЕ чтение `.md`-файла — запрет `Select-Object -Last` (см. `РЕЖИМ РАБОТЫ.md`) на stdout тестов НЕ распространяется.

**Что проверяет (текущий набор ~46 инвариантов):**
- Базовые симуляционные: `INV-TIME-GROW`, `INV-TICK-GROW`, `INV-NPC-MOVE`, `INV-NPC-NAME`, `INV-TRAV-DICT`, `INV-DIALOGUE-PIPELINE`, `INV-L3-EPHEMERAL`, `INV-DEATH-LOCK`, `INV-TRAV-ZOMBIE` и др.
- Каузальные/эпистемические: `INV-PLAYER-EPISTEMIC-CLOSURE`, `INV-EPISTEMIC-TRUST-MONOTONICITY`, `INV-EPISTEMIC-TRUTH-IMMUTABILITY`, `INV-REPLAY-DETERMINISM`, `INV-SAVE-LOAD-INTEGRITY`.
- AST-линтеры (запускаются как инварианты): `INV-DOMAIN-PURITY`, `INV-LLM-EXILE`, `INV-POSITION-MUTATION`, `INV-SPATIAL-SSOT`, `INV-FRONTEND-ISOLATION`, `INV-EPISTEMIC-BOUNDARY`, `INV-KERNEL-RNG`, `INV-WALL-CLOCK`, `INV-SILENT-FAILURE`, `INV-HP-SSOT`, `INV-NO-RETRO-SIM`, `INV-L1-APPEND-ONLY`.
- PBT (hypothesis): `INV-PBT-ROUNDTRIP`, `INV-PBT-SPATIAL`, `INV-PBT-TRAVERSAL`.
- Топология мира: `INV-WORLD-OBJECT-TOPOLOGY`, `INV-SC1-ZERO-POSITION`.

Точный актуальный список — список `INVARIANTS` в `backend/tests/IPT.py`. При добавлении нового линтера из `scripts/lint_*.py` он включается в IPT как инвариант (не более 15 симуляционных инвариантов — ограничение остаётся).

**Когда использовать:**
- Перед началом любого фикса → убедиться, что baseline зелёный.

## 1.1 ЛИНТ-СЬЮТ (`scripts/lint_*.py`) — статические выявители поломок

Лучшие инструменты проекта для выявления поломок и ошибок (кроме IPT) — это статические линтеры. Они не требуют запуска симуляции, мгновенны и покрывают архитектурные правила, которые runtime-тесты не видят. Большинство из них уже включены в IPT как инварианты, но для точечной проверки конкретного правила запускать их напрямую быстрее и вывод чище:

| `lint_kernel_rng.py` | `random.*` в симуляционном слое (ADR-O-301) | После работы с рандомизацией |

| `lint_retro_simulation.py` | Ретро-симуляция (обратная запись в прошлое) | После изменения persistence/replay |

**Правило выбора инструмента:**
1. Ошибка в архитектурном правиле (импорты, слои, мутации) → соответствующий `lint_*.py` точечно (вывод короткий).
2. Ошибка в инвариантах симуляции → IPT (только хвост вывода, см. §1).
3. Ошибка в конкретном модуле → pytest `tests/test_<name>.py -v`.
4. «Плавающий» баг → DriftLaboratory.

**Иерархия качества (что приоритетнее при диагностике):** lint_*.py (мгновенно, точно локализует) → IPT (5–60 сек, хвост вывода) → pytest (точечный модуль) → DriftLaboratory (воспроизведение) → Canary E2E (финальный smoke).

## 2. DriftLaboratory — прогон тиков без pygame / LLM / клиента

**Файл:** `backend/tests/sandbox/SUPERBOX/drift_laboratory.py`
**Запуск:** `cd backend && python -m tests.sandbox.SUPERBOX.run drift <mode>`

**Режимы:**
- `quick_debug` — 3 тика, видишь первый тик детально.
- `mass_traversal` — 200 тиков, измеряешь rate (comparisons/tick).
- `long_horizon` — длинный прогон для дрейфа идентичности.
- `save_load_storm` — стресс-тест save/load.
- `chunk_migration` — миграция между локациями.

**Назначение:** Единственный способ прогнать тики игры **БЕЗ запуска pygame, БЕЗ LLM-сервера, БЕЗ клиента**. Чистый pipeline в изоляции.

**Что показывает:**
- `comparisons` — сколько shadow vs legacy сравнений выполнено.
- `rate` = comparisons/tick — целевой показатель ≥0.5/tick.
- GATE-зонды: `[GATE_A]`, `[GATE_B1]`, `[GATE_B3]`, `[GATE_D2]`, `[GATE_E]`.
- `drift_B` — двойное создание traversal (должно быть 0 после ADR-O-201.4).

**Чтение вывода:**
```
[GATE_A]   life_intents=N        → LifeEngine генерирует интенты?
[GATE_B1]  accepted=N rejected=M → Spatial gate режет? (same-node collapse)
[GATE_B3]  reason=SUCCESS        → MovementEngine нашёл узел?
[GATE_B3]  reason=NODE_NOT_FOUND → Узел отсутствует в графе (data issue)
[GATE_D2]  compiled_thick=True   → Shadow Compiler скомпилировал?
[GATE_E]   validated=N applied=M → ProjectionEngine применил?
```

**Диагностический принцип:**
1. Сначала 3 тика (`quick_debug`) — видишь GATE-flow первого тика.
2. Если `GATE_B3 NODE_NOT_FOUND` → data issue (археология JSON).
3. Если `GATE_D2 compiled_thick=False` → EventCompiler (кодовый баг).
4. Если `GATE_B1 rejected=ALL` → позиции уже совпадают (state issue).
5. Потом 200 тиков (`mass_traversal`) — измеряешь rate.

**Критерий успеха:**
- `comparisons ≥ 100` за 200 тиков (rate ≥ 0.5/tick).
- `0 NameError / AttributeError` в логе.
- `GATE_B3 SUCCESS` для всех cross-location перемещений.
- `drift_B = 0`.

**Когда использовать:**
- После фикса в `TickOrchestrator`, `MovementEngine`, `EventCompiler`, `SceneStateManager`.
- Для воспроизведения «плавающего» бага — прогон 200 тиков, смотрим где ломается.
- Перед ADR Impact Audit — доказать, что фикс не внёс регрессию.

**Важно:**
- Копирует данные из `frontend/map_editor/campaigns/Open_road/`.
- Изменения JSON-файлов карт подхватываются автоматически.
- `__pycache__` должен быть очищен перед запуском (ЧАСТЬ I).
- `print()`-зонды ВИДНЫ в выводе; `logger.warning` — НЕТ (подавлен).

# ПРИНЦИПЫ ИСПОЛЬЗОВАНИЯ ТЕСТОВ

1. **Сначала IPT, потом фикс.** IPT зелёный = baseline не сломан. IPT красный = сначала восстанови baseline. Вывод IPT — только последние 3–10 строк (итоговый отчёт в конце, см. §1).
2. **Архитектурное правило нарушено → точечный линтер.** Не запускай тяжёлые тесты, если `scripts/lint_<name>.py` локализует проблему мгновенно (см. §1.1).
2. **DriftLaboratory для воспроизведения.** Если баг «плавающий» — 200 тиков DriftLaboratory найдут его.
3. **pytest для модулей.** После фикса в конкретном файле — запусти соответствующий `test_*.py`.
4. **LAST_SESSION.md после сессии.** Всегда читай отчёт CDS — там могут быть тихие деградации, которые ты не заметил.
5. **Не trust коду, trust логам.** Если думаешь «это вряд ли сломано» — запусти тест. Если тест зелёный — тогда trust.
6. **Один фикс = один тест.** Если починил баг — добавь или обнови тест, который покрывает этот кейс. Без теста фикс не считается завершённым.
7. **print() для диагностики, logger для production.** Во время отладки — `print()`. В коммите — `logger.debug()` с feature-флагом.

**КЛЮЧЕВАЯ ИДЕЯ:** Этот протокол — не бюрократия. Это единственный способ не утонуть в багах каузальной системы, где симптом виден на UI, а причина — в pipeline 5 фаз назад. Каждый шаг протокола существует потому, что без него предыдущий фикс сломал что-то ещё.
