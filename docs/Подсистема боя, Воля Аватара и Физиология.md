### 1. Что нужно сделать ПЕРЕД проектированием системы атаки (Заглушки)

Перед тем как писать `CombatResolver`, ты должен убедиться, что логика боёвки не будет обращаться к картинкам. Она должна обращаться к `Surface API`. Для этого в ядро и в `map_editor` вносятся следующие заглушки:

**А. Обновление формата сохранения Map Editor (Source of Truth)**
Сейчас твой редактор сохраняет стены как-то так: `{"type": "wall", "img": "wall.png"}`.
Ты должен изменить формат сохранения на `TileDTO` (даже если редактор пока не имеет UI для этих параметров):

```json
{
  "tile_id": "tavern_wall_01",
  "pos_x": 10,
  "pos_y": 5,
  "logic": {
    "surface_type": "solid",
    "base_noise": 0.3,
    "base_friction": 0.8
  },
  "visual": {
    "material": "medieval_brick",
    "dirt": 0.4,
    "seed": 12345
  },
  "render_placeholder": "debug_wall.png"
}
```
*Зачем:* Когда бой начнет рассчитывать урон от удара об стену, он запросит `surface_type` и `base_friction`, а не будет проверять имя картинки.

**Б. Создание DebugSurface (Заглушка среды)**
В коде создается класс-заглушка, который симулирует среду до тех пор, пока не появится генератор текстур:

```python
class DebugSurface(Surface):
    def __init__(self, logic_data: dict):
        self.type = logic_data.get("surface_type", "solid")
        
    def get_collision(self, x, y) -> float:
        return 1.0 if self.type == "solid" else 0.0

    def get_noise(self, x, y) -> float:
        return 0.5 # Дефолтный шум

    def get_friction(self, x, y) -> float:
        return 0.9 # Дефолтное сцепление
```

**В. Интеграция в CombatResolver (Правило)**
В правилах боёвки (Шаг 2) жестко прописывается: **Никаких проверок тайлов.** Только вызов `surface.get_friction()` или `surface.get_noise()`.

## 1. КРИТИЧЕСКИЕ АРХИТЕКТУРНЫЕ ИНВАРИАНТЫ (НЕНАРУШИМЫ)

Нарушение любого из нижеперечисленных пунктов = архитектурный баг и разрушение консистентности мира.

1.  **CombatResolver = Pure Function.** Внутри бойца нет состояния. На входе замороженные снимки состояния, на выходе — только дельта.
2.  **Три уровня защиты от мутации:**
    *   *Типы:* Только `frozen=True` dataclasses на входе и выходе (`NPCStateSnapshot`, `DamageDelta`). Физическая блокировка присваивания.
    *   *Изоляция RNG:* Случайность инкапсулирована. Запрещен глобальный `random()`. Используется инстанс `random.Random(rng_seed)`. Это дает детерминизм для тестов и защиту от побочных эффектов.
    *   *Возврат только Delta:* Внутри `CombatResolver` запрещены `db.write()`, `event_bus.publish()` и прямые изменения `NPCState`.
3.  **StateApplicator = Единственный мутатор.** Только `SqlitePersistenceAdapter.atomic_commit` применяет дельты к стейту (Устав §4.2.1).
4.  **EventBus = Транспорт.** Шина не трансформирует события. Вставлять логику классификации внутрь шины запрещено (Устав §5.1).

## 4. ИНТЕГРАЦИЯ В ФАЗОВУЮ МОДЕЛЬ (Устав §3)

### Фаза 1: Input -> IntentPreParser (НОВОЕ)
Ввод игрока проходит через `core/intent_preparser.py` **ДО** попадания в шину.
1. RegEx словарь ищет маркеры насилия. Если найдено — жестко классифицирует как `COMBAT_ACTION`.
2. Fallback -> LLM intent classifier.
3. Результат: `CombatIntentDTO`.

### Фаза 1.5: WillpowerGate (НОВОЕ)
Интент игрока проходит через Врата Воли в `services/player_cognition/willpower_gate.py`.
*   Это фильтр: `EventDTO -> WillpowerGate -> EventDTO`.
*   **Comply:** Пропускает `PLAYER_ATTACK_CONFIRMED`.
*   **Refuse:** Блокирует атаку, генерирует `AVATAR_REJECTED_INTENT` (Аватар глумится, действие отменяется).

### Фаза 2 & 3: EventBus & Memory
Событие атаки летит в шину. `MemoryProcessor` обновляет стейт.

### Фаза 5: Decision
`DecisionHub` цели работает стандартно. Пьяный Борко не реагирует (интент `idle`).

### Фаза 6: Resolution (Бой)
Из текущего `NPCState` создаются `NPCStateSnapshot` (для атакующего и защищающегося).
Вызывается `resolve_combat(snapshot_attacker, snapshot_defender, intent, rng_seed)`.
Возвращается `DamageDelta`. 

### Фаза 8/9: StateApplicator
`StateApplicator` применяет `DamageDelta` к `NPCState` через `SqlitePersistenceAdapter.atomic_commit`.

## 5. ЗАЩИТА ОТ СКРЫТЫХ ПРОБЛЕМ (Крайне важно для реализации)

1.  **Pain feedback loop:** Боль не должна линейно снижать защиту (иначе цикл: боль -> меньше защиты -> еще урон -> еще боль).
    *Решение:* `pain_effect = log(pain + 1)`.
2.  **Bleeding = Таймер смерти:** Линейное кровотечение скучно.
    *Решение:* `bleeding_rate * clotting_factor(time)` (свёртываемость крови со временем снижает скорость потери крови, если рона не смертельна).
3.  **Willpower abuse:** Игрок спамит безумные действия.
    *Решение:* При каждом `refuse` Аватар получает `stress_d`. После 3 отказов — игнорирует игрока на N тиков (cooldown).
4.  **Corpse = Event bomb:** Труп вызывает панику у каждого входящего НПС.
    *Решение:* Труп излучает `WITNESS_DEATH` эвенты с `decay` (затухание). Через 3 тика паника сменяется привычкой.

## 1. КОНЦЕПТУАЛЬНАЯ МОДЕЛЬ

Игрок (Source: `player`) и Аватар (NPC: `avatar_player`) — это два сознания в одном теле.
*   **Игрок** генерирует `IntentDTO` (желания).
*   **Аватар** — это физическая оболочка со своими потребностями (голод, сон, страх) и характером.
*   Если `IntentDTO` противоречит состоянию Аватара, `DecisionHub` Аватара отклоняет интент и генерирует собственный `CommunicationIntent` (отказ, глумление или торг).

**Правило:** Аватар — это такой же NPC, проходящий через 10 фаз тика, просто его `Input` (Фаза 1) формируется из текста игрока, а не из `WorldTick`.

## 2. НОВЫЕ СУЩНОСТИ В СЛОЕ DOMAIN (Закон 1.2)

Никакой логики, только данные. Добавляем в `backend/app/domain/`.

```python
    pain: float        # 0.0 (здоров) - 100.0 (агония)
```

```python
    stress_delta: float   # Сколько стресса получил Аватар за подавление воли
```

## 3. ИНТЕГРАЦИЯ В ФАЗОВУЮ МОДЕЛЬ (Устав §3)

Аватар не ломает фазы, он использует их.

### ФАЗА 1: Input
Игрок пишет: *"Нападу на стражника"*.
Система создает стандартный `EventDTO(type=PLAYER_INTENT, payload={"action": "attack", "target": "guard_borko"})`.

### ФАЗА 3: Memory Phase
`MemoryProcessor` обновляет `NPCState` Аватара. Если Аватар голоден (`hunger > 70`), в его state появляется флаг `urgency: survive`.

### ФАЗА 4: Pre-Decision (Ключевая точка!)
`TopicExtractor` Аватара читает `PLAYER_INTENT` + свой `NPCState`.
*   Если Игрок хочет драться, а Аватар голоден и труслив, `TopicExtractor` формирует тему: **"отказ от боя из-за голода и страха"**.
*   Закон 2.2.1 соблюден: `topic` не пустой.

### ФАЗА 5: Decision (Механика Воли)
`DecisionHub` Аватара вызывает `WillpowerEngine.compute(intent, avatar_state)`.
1.  **Comply (Подчинение):** Воля игрока сильна. Аватар выполняет, но получает `stress_d`.
2.  **Reluctant (Нехотя):** Аватар выполняет, но `DecisionHub` генерирует `CommunicationIntent` с жалобой/стоном.
3.  **Refuse (Отказ):** Аватар игнорирует команду. Создается `CommunicationIntent` с глумлением ("Сам иди бейся, олимпиец, у меня руки трясутся!").
4.  **Counter-Offer (Торг):** Аватар предлагает сделку. ("Я ударю его, если ты заставишь Торнина накормить меня").

### ФАЗА 6: Post-Decision
`IntentEventAdapter` превращает решение Аватара в `EventDTO`.
*   Если `Comply` -> `EventDTO(type=PLAYER_ATTACKED)`.
*   Если `Refuse` -> `EventDTO(type=AVATAR_REJECTED_INTENT)`.

### ФАЗА 7: EventBus
События летят в шину. Если `AVATAR_REJECTED_INTENT`, фронтенд получает текстовый ответ от Аватара, а боевая система **не активируется**.

## 4. МЕХАНИКА ТОРГА (Обмен)

Это не отдельный режим, это цикл `EventDTO`.

1.  **Игрок:** "Укради у Горана кошелек" (`PLAYER_INTENT`).
2.  **Аватар (Фаза 5):** WillpowerCheck = `Counter-Offer`. Тема: "требую еды за риск".
3.  **Аватар (Фаза 7):** Публикует `EventDTO(type=AVATAR_COUNTER_OFFER, payload={"demand": "food", "action": "steal"})`.
4.  **Фронтенд:** Показывает текст Аватара: *"Сначала жратва, потом работа. Я не собака, чтобы служить за так"*.
5.  **Игрок:** "Ладно, я попрошу Торнина дать тебе похлебку" (`PLAYER_INTENT`).
6.  **Система:** Выполняет действие с Торниным. `NPCState` Аватара обновляется (`hunger` падает).
7.  **Игрок:** "Теперь кради" (`PLAYER_INTENT`).
8.  **Аватар (Фаза 5):** WillpowerCheck = `Comply` (голод утолен, риск оправдан).
