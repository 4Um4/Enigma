# COMPARISON REPORT: V.0.5.2.0 vs V.0.5.1.9

База сравнения:
- От: `origin/V.0.5.1.9_Продолжаю_починку_5`
- До: `origin/V.0.5.2.0_Починил_запуск_игры`
- Коммит: `b0d0a17`

## 1. Критический параметр решения
Ключевой параметр: **рост управляемости игрового цикла и памяти NPC при снижении монолитности**.

Что это значит практически:
- Игровой loop перестал быть одной перегруженной точкой отказа и разбит на специализированные модули.
- Память NPC получила отдельный контур с переносом данных в SQLite + экспортом + правилами промоции.
- Появилась проверяемость новых правил через тесты (29 новых `test_*`).

## 2. Возможные сценарии при минимальном смещении входных данных
Сценарий A (наиболее вероятный):
- При тех же игровых действиях пользователя система чаще проходит тик без деградации состояния.
- Причина: вынос инициализации сцены, времени, state-хелперов, фабрики сервисов.

Сценарий B:
- Поведение NPC становится более устойчивым на длинных сессиях.
- Причина: SQLite-store для памяти + batch/ordered загрузка + контроль decays/compression/identity.

Сценарий C:
- Ускоряется локализация багов в запуске игры.
- Причина: модульная композиция вместо монолита (`game_loop/__init__.py` существенно разгружен).

## 3. Что может перевернуть итоговый вывод
- Отсутствие `pytest` в окружении сейчас не дало прогнать тесты фактически (модуль `pytest` не установлен). Пока валидность основана на структуре изменений, а не на runtime-прохождении.
- Есть изменения в session/save JSON; если это тестовые артефакты, они могут вносить шум в дифф и побочные эффекты при загрузке состояния.
- Переход к SQLite может выявить латентные race/locking-эффекты при параллельных тиках, если режим записи станет многопоточным.

## 4. Альтернативные варианты с вероятностной оценкой (0-100%)
1. **Текущий путь (принят): модульная декомпозиция + SQLite + тестовый каркас** — **78%**
Плюсы: масштабируемость, ясные точки расширения, выше наблюдаемость ошибок.
Риски: усложнение интеграции между сервисами, необходимость дисциплины DI.

2. **Консервативный путь: точечные фиксы в монолите без нового memory-контура** — **14%**
Плюсы: меньше немедленных изменений.
Риски: возврат техдолга, слабая предсказуемость на длинных сессиях.

3. **Агрессивный путь: сразу полная событийная архитектура (event bus/worker)** — **8%**
Плюсы: максимум расширяемости.
Риски: высокий шанс регрессии запуска игры и долгий stabilization.

## 5. Краткий, но глубокий вывод
За день сделан **не косметический**, а **архитектурно-функциональный сдвиг**:
- В диффе: `41` файл, `+3092/-1282`.
- Новых production-модулей: `7`.
- Новых тестовых модулей: `4`.
- Новых тест-кейсов: `29`.

Ценность не в объёме строк, а в трёх результатах:
- Разделён критический контур game loop (снижение хрупкости запуска).
- Память NPC переведена в более зрелый жизненный цикл (decay/compress/identity + SQLite persistence + YAML export).
- Появилась основа для воспроизводимой проверки поведения, а не ручного «прощупывания».

Итог: версия `V.0.5.2.0` объективно ближе к **стабильной платформе**, чем `V.0.5.1.9`, даже если часть runtime-рисков ещё требует прогона тестов в окружении с установленным `pytest`.
