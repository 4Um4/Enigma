## 1. Критический параметр решения

Ключевой параметр релиза: **переход от “боевой подсистемы” к физико-каузальному контуру мира**.

Что это значит технически:
- `Physiology` встроен в ядро тика (`Phase 0.5` + `Phase 8`), а не вынесен в отдельный “режим боя”.
- Появился мост `EventDTO -> ImpactIntentDTO -> PhysiologyPayload` (`CombatSubscriber` + `ImpactEngine`).
- Введён DRSL-подход к агрегации (`ReductionPolicy`): бухгалтерские домены редуцируются алгебраически, физиология проходит как инерционные инъекции (`PHYSICS_COMPOSITE`).

Системный смысл: релиз меняет **онтологию состояния**, а не только API.

---

## 2. Возможные сценарии при минимальном смещении входных данных

1. Сценарий «высокая сила удара + низкая уклоняемость цели».
Результат: каскад `Force -> Pain/BloodLoss -> Shock -> Emotion` проходит сквозь тик детерминированно (подтверждено e2e-тестом).

2. Сценарий «много дельт в одном тике по разным доменам».
Результат: социальные/эмоциональные дельты сворачиваются, физиология не теряется в merge, а проходит отдельно.

3. Сценарий «idle-симуляция без действий игрока».
Результат: время и инерционные процессы продолжают идти, что снижает класс багов “мир замер без инпута”.

4. Сценарий «перенос позиции NPC из backend в frontend».
Результат: force-merge world snapshot уменьшает рассинхрон render/state при player action.

## 3. Что может перевернуть итоговый вывод

- Дублирование DRSL-конституции (`ReductionPolicy/DELTA_POLICY_REGISTRY`) одновременно в `state_delta.py` и `tick_orchestrator.py` создаёт риск расхождения правил редукции.
- Интенсивные изменения в `tick_orchestrator.py` и `frontend/game_screen.py` повышают вероятность скрытых регрессий на длинных игровых сессиях.
- CFRM пока частично формализован (модели есть, полный runtime-переход не завершён): главный выигрыш архитектуры ещё впереди.

## 4. Альтернативные варианты с вероятностной оценкой (0-100%)

- Вариант A: продолжать текущую стратегию (Physiology + DRSL + CFRM migration) — **72%**.
Плюс: согласованный причинный путь, масштабируемость доменов.
Минус: высокая цена дисциплины контрактов на каждом шаге.

- Вариант B: откатить физику к “обособленной Combat-системе” — **8%**.
Плюс: быстрее локально.
Минус: возврат domain leakage и повтор старых архитектурных ошибок.

- Вариант C: заморозить runtime и делать только UI/визуал — **20%**.
Плюс: видимый UX-прирост коротко.
Минус: накопление скрытого архитектурного долга в симуляции.
